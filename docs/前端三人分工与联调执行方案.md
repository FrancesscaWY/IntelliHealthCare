# 前端三人分工与联调执行方案

更新时间：`2026-04-22`

本文档基于以下实际材料整理：

- 后端 API 手册：[backend-api-manual.md](./backend-api-manual.md)
- Swagger 联调手册：[frontend-api-integration-guide.md](./frontend-api-integration-guide.md)
- 成员协作手册：[member-development-manual.md](./member-development-manual.md)
- 当前前端目录：`apps/user-web/src/pages/**`、`apps/admin-web/src/pages/**`
- 当前 Swagger 联调地址：`http://server.mctown.online:8190/api/v1/docs`

本文档目标只有三个：

1. 将现有前端页面与后端 API 模块做一一对应分工
2. 让三名前端成员明确自己负责的页面目录、接口范围和联调链路
3. 统一三名前端成员的开发方法、联调流程、交付物和阻塞处理方式

---

## 1. 当前协作背景

当前前端实际分为两个工作区：

- 用户端：`apps/user-web`
- 后台端：`apps/admin-web`

当前后端 API 文档按四层组织：

- 系统层
- 用户端
- 后台端
- 内部治理层

对前端开发来说，本轮工作只需要直接使用以下三层：

- 系统层：健康检查、公开协议
- 用户端：面向 `apps/user-web`
- 后台端：面向 `apps/admin-web`

内部治理层 `/internal/*` 不作为本轮普通前端页面直接接入范围。

---

## 2. 分工原则

本次三人分工遵循以下原则：

1. 按完整业务链路拆分，而不是按零散页面拆分。
2. 尽量保持页面目录完整，避免同一目录被两个人长期交叉维护。
3. 一个 API 模块原则上只对应一个前端 owner，减少联调口径冲突。
4. 后台端和共享联调基座必须有明确 owner，避免“大家都能改，最后没人收口”。
5. 每个人都要对自己负责范围内的 Swagger 测试、页面接入、自测和提测结果负责。

## 3. 三人分工总览

| 成员 | 角色定位 | 主工作区 | 负责页面目录 | 对应 API 模块 | 核心交付目标 |
| --- | --- | --- | --- | --- | --- |
| 成员 A | 用户入口与内容社区负责人 | `user-web` | `onboarding`、`auth`、`home`、`content`、`community` | 用户认证、用户中心、首页、定位、搜索、消息与咨询、健康内容、社区与活动、公开协议 | 完成用户登录、首页、我的、消息、资讯、社区链路接入 |
| 成员 B | 服务交易与档案中心负责人 | `user-web` | `service`、`orders`、`healthdocs` | 家庭与地址、服务目录、订单与预约、支付、体检报告、文件上传、健康档案 | 完成服务浏览、下单支付、订单履约、档案与报告链路接入 |
| 成员 C | 健康管理与后台联调负责人 | `user-web` + `admin-web` | `health`、`diet-record`、`admin-web/src/pages` | 健康数据与设备、健康膳食与自测、AI 助手、后台认证、后台工作台、后台订单调度、后台报告审核 | 完成健康管理链路、后台工作台链路、共享联调基座收口 |

补充说明：

- 成员 C 兼任前端联调负责人，负责统一请求封装、错误处理口径、环境变量接入口径和联调验收收口。
- 成员 A 与成员 B 只在公共封装确有复用时修改共享层，避免无边界扩散。
- 本文中的“owner”是默认责任人，不等于只能由本人修改，但提测和交付必须由 owner 收口。

### 7.1 开工前准备

每个人开工前必须完成：

1. 先在本文 `4.2`、`5.2`、`6.2` 中找到自己负责的页面行，确认页面路径、中文名称、API 模块、关键接口和是否为预留页。
2. 阅读 [backend-api-manual.md](./backend-api-manual.md) 中自己负责的 API 分册。
3. 阅读 [frontend-api-integration-guide.md](./frontend-api-integration-guide.md) 中 Swagger 联调方法。
4. 在 Swagger 页面手工执行至少 3 个自己负责页面的关键接口。
5. 对“当前无直接接口”的页面先标记 `mock / 待后端补接口`，不要自行发明字段。
6. 确认测试账号、token 填写方式和返回结构格式。

### 7.2 页面接入的标准方法

每个页面接入真实 API 时，统一按以下顺序：

1. 先在本文页面级矩阵中找到该页面，确认路径、中文名称、owner、API 模块和关键接口。
2. 再去 [backend-api-manual.md](./backend-api-manual.md) 对应章节核对 path、query、body、response 结构。
3. 再到 Swagger 同名标签，把本页矩阵里列出的关键接口先手工跑通。
4. 记录成功请求所需的 path、query、body 样例。
5. 确认页面到底需要列表、详情、提交、上传还是状态轮询。
6. 如果页面是“目录存在但未登记 manifest”的预留页，先确认 route/manifest 是否补齐，再接真实接口。
7. 如果页面“当前无直接接口”，先保持 mock 或占位，并提交补接口问题，不要硬写伪接口。
8. 先完成页面数据结构与 API 返回结构的映射。
9. 再把页面从 mock 切换到真实请求。
10. 补齐加载态、空态、失败态、无权限态。
11. 最后做一次页面真实点击路径自测。

### 7.3 代码放置方法

遵循当前仓库页面优先原则：

- 逻辑只服务当前页面时，优先放在当前页面目录或当前分组目录。
- 两个及以上页面复用时，再提取到应用内共享层。
- 跨用户端和后台端都要用的工具，再由成员 C 统一判断是否进入公共层。

不要做的事情：

- 借联调名义顺手重构整个前端结构。
- 在没有复用依据时提前抽象复杂 service 层。
- 一边改共享层一边改多个业务域，导致问题难以定位。

### 7.4 Swagger 联调的统一口径

所有人都使用同一套 Swagger 联调步骤：

1. 打开 `http://server.mctown.online:8190/api/v1/docs`
2. 先执行 `GET /system/health`
3. 用户端先登录拿 `APP_TOKEN`
4. 后台端先登录拿 `ADMIN_TOKEN`
5. 在右上角 `Authorize` 中填 `Bearer accessToken`
6. 按本文页面矩阵中写明的模块顺序，先测列表接口，再测详情接口，再测提交接口

统一要求：

- 每个页面接入前，至少先在 Swagger 上手工成功执行一次本文矩阵中列出的关键接口。
- Swagger 标签必须和 API 手册章节一一对应查看，优先按 `系统层 / 模块`、`用户端 / 模块`、`后台端 / 模块` 的顺序找接口。
- 对于“当前无直接接口”的后台预留页，只能记录缺失并先 mock，不能擅自复用不属于该端的接口充数。
- 出现问题时必须保留接口路径、请求参数、返回体和 `requestId`。
- 不允许只凭 API 名称猜字段含义。

### 7.5 每日工作节奏

建议三个人统一按以下节奏推进：

上午：

1. 明确当天页面目标
2. 在 Swagger 上先跑通对应接口
3. 确认是否存在接口阻塞

下午：

1. 完成页面真实接口接入
2. 处理加载态、错误态和边界情况
3. 做页面自测

下班前：

1. 输出已完成页面清单
2. 输出待后端确认问题清单
3. 输出第二天接续计划

## 8. 三人之间的依赖关系

### 8.1 成员 A 对成员 B、C 的依赖

- 成员 A 完成用户端登录和基础用户态口径后，成员 B、C 的用户端页面可直接复用。
- 成员 A 需要将 `APP_TOKEN` 获取、失效处理和用户信息字段口径同步给成员 B、C。

### 8.2 成员 B 对成员 A 的依赖

- 成员 B 的所有用户端业务接口都依赖用户登录态。
- 如果成员 A 还未完成登录态接入，成员 B 仍需先在 Swagger 上完成接口验证，不得停工等待。

### 8.3 成员 A、B 对成员 C 的依赖

- 成员 C 负责统一请求基座和后台登录态处理。
- 成员 A、B 如果需要抽取共用请求工具，应先与成员 C 对齐。
- 成员 C 负责统一收集三人联调阻塞，并给出优先级和升级路径。

## 9. 提测标准

每个成员在提测前必须确认：

1. 自己负责目录下的目标页面已经切到真实 API。
2. 对应工作区能正常启动。
3. 对应工作区 `check` 通过。
4. 至少完成一条核心业务路径的端到端自测。
5. Swagger 对应接口能独立复现成功调用。

建议命令：

用户端整站：

```bash
npm run dev:user
npm run check:user
```

用户端单页：

```bash
npm run dev:page -- --page <page-id>
```

后台端整站：

```bash
npm run dev:admin
npm run check:admin
```

后台端单页：

```bash
npm run dev:admin:page -- --page <page-id>
```

## 10. 阻塞问题提报模板

当发现接口或 Swagger 与页面需求不一致时，三人统一按以下格式提报：

```text
页面：
接口：
请求方式：
请求参数：
期望结果：
实际结果：
requestId：
是否阻塞当前页面：
建议优先级：高 / 中 / 低
```

禁止只提“接口不对”“字段不够”“Swagger 有问题”这种无法执行的描述。

## 11. 建议执行顺序

为了减少三人互相等待，建议整体按以下顺序推进：

第一阶段：

- 成员 A：登录、首页、用户中心
- 成员 B：服务目录、预约与订单主链路
- 成员 C：后台登录、后台首页、健康数据总览

第二阶段：

- 成员 A：消息、内容、社区
- 成员 B：支付、文件上传、报告、档案
- 成员 C：设备、用药、膳食、自测、后台订单/报告

第三阶段：

- 成员 A：用户侧边界页和长尾详情页
- 成员 B：订单售后、履约、报告解读完善
- 成员 C：AI 增强接口、后台补页、联调总回归

---

## 12. 一句话结论

本轮三名前端的正确推进方式不是“各自挑页面做”，而是：

- 成员 A 负责用户入口、首页、内容社区
- 成员 B 负责服务交易、订单支付、档案报告
- 成员 C 负责健康管理、后台端和联调整体收口

三个人统一通过 API 手册和 Swagger 联调，不凭猜测接字段，不跨域抢 owner，不把阻塞问题留到提测后再暴露。
