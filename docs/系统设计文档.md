# IntelliHealthCare 系统设计文档

> 更新时间：`2026-04-25`
>
> 文档定位：正式系统设计文稿
>
> 依据范围：`apps/user-web`、`apps/admin-web`、`apps/backend`、`packages/page-core`、`apps/backend/prisma/schema.prisma`、`apps/backend/scripts/build-rag-db.ts`、`apps/backend/scripts/eval-rag.ts`

## 摘要

IntelliHealthCare 是一套面向长者、家属与机构运营团队的智慧康养平台。系统围绕“健康数据持续沉淀、服务交易闭环履约、内容与互动提升活跃度、AI 能力增强服务决策”四条主线构建。其总体设计并未采用多系统分拆的传统路径，而是以 `npm workspaces` 管理的 Monorepo 为工程载体，以 `NestJS` 模块化单体作为统一业务中台，以 `PostgreSQL + Prisma` 承载主数据，以 `Redis/BullMQ` 承载异步任务与智能体调度，以 `MinIO` 统一文件对象存储，并在后端内部嵌入 RAG 与 Hermes 多智能体运行时。

本设计的核心判断是：在养老健康场景中，数据强耦合、权限边界复杂、风险治理要求高，系统更适合采用“统一业务底座 + 受控智能增强”的设计路线，而不适合在早期阶段将健康档案、服务交易、消息互动、知识检索和多智能体执行拆散为多个独立平台。基于这一判断，IntelliHealthCare 将 AI 能力设计为后端内部的一等子系统，而非外挂能力：RAG 负责将平台知识、机构知识与个体知识组织成可检索、可引用、可评测的知识底座；Hermes 负责以受控多智能体方式完成任务标准化、领域协同、工具调用、风险审查、人工复核与审计留痕。

因此，IntelliHealthCare 的系统设计不是“前端 + CRUD 后端 + AI 接口拼接”的简单叠加，而是一个以业务域为中心、以统一数据模型为基础、以知识检索与多智能体为增强层、以治理链路为约束层的整体系统。

## 1. 引言

### 1.1 编写目的

本文档用于以正式文稿方式阐述 IntelliHealthCare 的系统设计思想、逻辑结构与关键机制，重点回答以下问题：

- 为什么系统采用当前的总体架构，而不是微服务或独立 AI 平台架构；
- 用户端、后台端、后端与 AI 子系统之间如何形成一致的逻辑闭环；
- RAG 如何作为知识基础设施支撑用户查询、后台运营与多智能体执行；
- Hermes 多智能体框架如何在受控边界内完成任务编排、领域协同与风险治理。

### 1.2 适用范围

本文档面向以下读者：

- 项目立项、评审与验收参与者；
- 架构评审、技术答辩与方案论证参与者；
- 需要理解系统整体设计逻辑的研发负责人、算法负责人和产品负责人；
- 需要了解 AI 子系统边界、治理机制与数据流的合规、运营与实施人员。

本文档不是接口手册，不展开逐个接口说明；也不是成员开发手册，不说明日常开发命令与脚手架操作。

### 1.3 设计原则

IntelliHealthCare 当前系统设计遵循以下原则：

- 统一业务底座原则：健康、服务、内容、消息与 AI 共用一套核心数据底座与权限体系。
- 模块化单体原则：在业务耦合度高且演进仍快速的阶段，优先保证系统一致性与交付效率，而非过早分布式拆分。
- 受控智能增强原则：AI 只在明确的工具边界、权限边界和审计边界内参与执行，不绕过业务规则。
- 知识分层原则：公共知识、机构知识与用户私有知识必须分层建模、分层检索、分层授权。
- 可审计原则：所有高价值或高风险 AI 执行均应保留任务记录、推理痕迹摘要、工具调用摘要和人工决策结果。
- 渐进演进原则：先建设统一运行底座与核心链路，再扩充产品入口和多 Agent 协作深度。

## 2. 系统定位与设计约束

### 2.1 系统定位

IntelliHealthCare 的业务目标不是单一的健康档案系统，也不是单一的养老服务电商系统，而是一个同时覆盖用户生活服务、健康理解、风险运营、机构协同和智能助手能力的智慧康养平台。系统服务的核心对象包括：

- 长者用户：关注个人健康数据、报告、设备、服务和日常照护；
- 家属用户：关注授权范围内长者的健康状态、风险提醒和服务安排；
- 机构运营与专业人员：关注长者全景档案、订单履约、服务排班、风险预警和运营分析；
- 平台治理与运营人员：关注内容质量、消息触达、知识管理、智能体治理和系统配置。

由此可见，系统的设计对象天然跨越多个业务域，且这些业务域之间存在强数据关联。例如，服务推荐需要参考健康档案，风险分诊需要引用近期报告和指标，后台 Copilot 需要聚合健康、服务、风险、设备和内容多个领域的摘要。因此，系统设计必须优先保证跨域数据的一致性与权限可控性。

### 2.2 设计约束

系统设计同时受到以下约束：

- 养老健康场景属于高敏感、高责任场景，AI 输出不能脱离治理直接自动执行；
- 用户私有健康资料与机构资源信息具有不同的可见域，必须进行严格隔离；
- 系统需要同时支撑用户端和后台端两类截然不同的交互模式；
- 当前项目仍处于快速迭代阶段，需要在架构稳定性与研发效率之间取得平衡；
- AI 能力必须允许降级运行，不能因外部模型网关短暂不可用而导致系统完全失效。

这些约束决定了 IntelliHealthCare 不应被设计为一个“开放自治的 AI 平台”，而应被设计为一个“以业务系统为中心、AI 在其中受控运行”的统一平台。

## 3. 总体设计

### 3.1 总体架构选择

IntelliHealthCare 当前采用“前后端分离 + 后端模块化单体 + 内嵌 AI 子系统”的总体架构。其核心原因在于：

- 健康档案、指标、报告、服务交易、消息互动和知识检索之间共享同一用户与授权模型；
- 高风险领域需要统一的审计、复核与人工干预入口；
- 当前阶段的主要挑战在于形成完整闭环，而非解决超大规模分布式吞吐问题；
- AI 执行需要紧贴业务上下文与权限判断，脱离主业务后端会显著提高一致性成本。

因此，系统并未将健康系统、服务系统、CMS、消息中心和 AI 平台拆分为多个独立服务群，而是在统一后端中以模块方式组织这些能力。

### 3.2 总体结构

```text
长者 / 家属                         机构运营 / 医生 / 护理 / 平台管理员
    |                                                |
    v                                                v
apps/user-web                                   apps/admin-web
    |                                                |
    +------------------------- HTTP/REST ------------+
                              /api/v1
                                  |
                                  v
                        apps/backend (NestJS)
        /system      /app      /admin      /internal/agents
           |           |          |                |
           +-----------+----------+----------------+
                                  |
             +--------------------+--------------------+
             |                    |                    |
             v                    v                    v
        PostgreSQL          Redis + BullMQ          MinIO
             |
             +--> RAG Knowledge Layer
             |
             +--> Hermes Multi-Agent Runtime
             |
             +--> Audit / Human Review / Governance
```

### 3.3 总体分层

从逻辑上看，系统可以分为五层：

- 交互层：用户端与后台端，分别承接移动化服务交互和运营工作台交互。
- 应用层：后端控制器、应用服务与模块服务，对外提供统一 API。
- 领域层：用户、家庭、健康、服务、交易、内容、消息、后台和 AI 等领域模块。
- 基础设施层：数据库、队列、对象存储、Swagger、配置校验与请求治理。
- 智能增强层：RAG 知识系统、Hermes 多智能体运行时、模型网关与治理链路。

这一分层方式的关键含义在于：AI 并不是独立于业务层之外的横向外挂，而是位于“领域层之上、基础设施之上”的智能增强层，必须以业务域、工具边界和权限边界为前提。

## 4. 应用与领域设计

### 4.1 用户端设计

用户端 `apps/user-web` 面向长者与家属，采用 `Vue 3 + TypeScript + Vite` 实现。其设计目标不是构建一个复杂的多路由门户，而是提供一套围绕健康、服务、内容、消息和 AI 入口的统一用户体验。

当前用户端的设计具有两个显著特征：

- 页面组织采用 manifest 驱动，保证页面是可登记、可发现、可预览的明确资产；
- 运行态采用 `vue-router` 组织页面导航，但页面组件仍通过动态发现机制装载，从而兼顾正式路由与页面协作效率。

在产品结构上，用户端并非仅仅承担展示作用，而是直接承接 AI 服务消费场景，包括：

- 智能助手会话；
- AI 健康摘要；
- AI 报告解读；
- AI 服务推荐与预约预填；
- AI 风险提醒与知识检索。

因此，用户端在整个系统中既是业务交互前台，也是 AI 能力的主要消费前台。

### 4.2 后台端设计

后台端 `apps/admin-web` 面向机构运营、医生、护理、客服及平台管理人员。与用户端不同，后台端当前采用 manifest 驱动的单壳工作台模式，而不是完整的 URL 路由后台框架。

这一设计符合后台场景的当前阶段需求：一方面，后台工作台需要快速承载不同业务域页面；另一方面，后台页面常用于原型深化、运营联调与管理流程整合，采用单壳 + 页栈导航有利于维持统一工作台体验。

后台端重点承接以下场景：

- 长者画像与档案全景查看；
- 订单、工单、售后与评价管理；
- 服务人员、商品、机构与账号配置；
- 风险预警、消息活动与内容运营；
- 运营分析与智能摘要 Copilot。

这决定了后台端不仅是管理端 UI，更是 Hermes 与 RAG 能力的重要应用面。

### 4.3 后端领域模块设计

后端 `apps/backend` 是系统的统一业务核心。当前所有业务模块被装配在同一个 NestJS 进程中，但在逻辑上已按领域进行拆分。

| 领域 | 模块 | 主要职责 |
| --- | --- | --- |
| 系统治理 | `SystemModule` | 健康检查、架构摘要、系统级可发现性 |
| 身份与权限 | `AuthModule` | 用户端登录、后台登录、JWT、RBAC、内部访问控制 |
| 用户与家庭 | `UsersModule`、`FamilyModule` | 用户资料、首页聚合、定位搜索、家庭绑定、地址 |
| 健康档案 | `HealthArchiveModule` | 基础档案、病史、长期健康资料 |
| 健康数据 | `HealthMetricsModule` | 指标、设备、告警、用药、趋势数据 |
| 健康生活方式 | `HealthLifestyleModule` | 饮食、食谱、自测与生活方式辅助数据 |
| 服务与交易 | `ServiceCatalogModule`、`OrdersModule`、`PaymentsModule` | 服务目录、预约下单、支付确认、工单与售后 |
| 报告与文件 | `ReportsModule`、`FilesModule` | 报告归档、报告审核、预签名上传、文件元数据 |
| 消息与互动 | `MessagingModule` | 通知、会话、后台消息活动 |
| 内容与社区 | `ContentModule`、`CommunityModule` | 健康资讯、讲堂、疾病知识、社区与活动 |
| 后台管理 | `AdminModule` | 后台工作台、机构、账号、商品、分析配置 |
| AI 子系统 | `AgentsModule` | Hermes 运行时、RAG、工具层、治理、内部与用户 AI 接口 |

该模块划分说明后端的边界是“按稳定业务域拆分”，而不是“按前端页面或接口路径拆分”。这也是后续 Hermes 使用共享领域 Agent 的前提。

## 5. 数据与基础设施设计

### 5.1 主数据架构

系统当前采用单 `PostgreSQL` 实例作为核心业务数据库，并通过 `Prisma` 作为唯一正式 ORM 访问层。此设计的重点不在于强调单库，而在于建立统一主数据源，确保以下关键实体在所有业务域中具有一致语义：

- 用户、角色与组织关系；
- 健康档案、指标、设备、报告；
- 服务目录、订单、工单、支付与售后；
- 内容、活动、消息与互动记录；
- Agent 任务、复核记录、审计日志和 RAG 知识数据。

当前 Prisma 模型数量为 `66` 个，已形成“单库多域”的稳定结构。该结构使得跨域查询和 AI 上下文拼装可以在统一语义模型上进行，而无需跨库聚合。

### 5.2 队列与异步架构

系统使用 `Redis + BullMQ` 作为异步任务底座。其主要用途不是实现通用消息平台，而是为以下场景提供可靠异步执行能力：

- Hermes 智能体任务入队与执行；
- 失败重试与重试退避；
- 后台或事件驱动型高耗时任务处理；
- 风险治理和人工复核前的任务持久化。

因此，Redis 在本系统中的职责主要体现在“异步执行控制”而非“缓存命中优化”。

### 5.3 文件与对象存储架构

系统使用 `MinIO` 作为 S3 兼容对象存储。文件流设计采用“后端签发预签名 URL、前端直传对象存储、后端回填文件元数据”的方式。该设计的优势在于：

- 降低后端在大文件上传链路中的二进制转发压力；
- 使文件访问地址和对象生命周期保持统一管理；
- 将文件权限与业务元数据仍留在后端控制之下。

### 5.4 横切治理机制

后端已建立统一的横切治理机制：

- 所有请求统一分配或透传 `x-request-id`；
- 所有成功响应统一封装为标准结构；
- 所有异常统一映射为业务错误码；
- 所有受保护接口统一经过 JWT 与角色控制；
- 所有内部 Agent 接口额外叠加来源 IP 与共享密钥约束。

这意味着，系统在技术层面已经具备“统一治理入口”的设计基础，而不是由各模块自行约定协议与错误语义。

## 6. RAG 系统设计

### 6.1 设计目标

RAG 在 IntelliHealthCare 中的角色不是简单的“给大模型补充几段上下文”，而是整个 AI 子系统的知识基础设施。其目标包括：

- 将平台规则、服务目录、公共健康知识、机构资源与用户私有资料组织为可检索知识资产；
- 为用户端知识查询、后台检索和 Agent 工具调用提供统一知识入口；
- 为多智能体输出提供可引用、可追溯的证据来源；
- 为知识质量建立可构建、可评测、可回归的闭环。

因此，RAG 在本系统中是一个完整子系统，而非单一算法模块。

### 6.2 知识分层设计

系统当前以 `RagKnowledgeType` 和 `RagVisibilityScope` 为核心，将知识划分为五类：

| 知识类型 | 说明 | 典型来源 |
| --- | --- | --- |
| `SERVICE_CATALOG` | 服务目录与服务规则知识 | `ServiceItem`、机构信息 |
| `HEALTH_KNOWLEDGE` | 公共健康知识与医学科普知识 | 外部公开页面、文章、讲堂、疾病知识 |
| `PLATFORM_RULE` | 平台治理规则与系统边界知识 | 文档、规则定义、平台约束 |
| `INSTITUTION_RESOURCE` | 机构资源、排班与能力知识 | `Institution`、`Staff`、`StaffSchedule` |
| `USER_PRIVATE_ARCHIVE` | 用户私有档案与个体资料知识 | 报告、档案、历史健康数据 |

同时，系统使用三类可见域控制知识边界：

- `PUBLIC`：面向公共查询；
- `INSTITUTION`：面向机构内可见知识；
- `USER_PRIVATE`：面向经授权的用户私有知识。

这种设计的价值在于，知识分类与权限模型在同一套数据结构上完成，避免了“先检索后再猜权限”的不严谨设计。

### 6.3 RAG 数据模型

RAG 数据模型由以下实体构成：

- `RagKnowledgeBase`：知识库定义层，描述知识库的类型、可见域、来源配置、分块配置与刷新策略；
- `RagDocument`：文档层，表示一篇可引用的原始知识文档；
- `RagChunk`：检索层，表示面向召回与排序的最小检索单元；
- `RagIngestionRun`：构建层，记录一次导入或重建任务的执行结果；
- `RagEvalRun` 与 `RagEvalCaseResult`：评测层，记录检索质量评测与案例结果。

这一建模方式体现出 RAG 的完整生命周期：

```text
知识库定义 -> 文档入库 -> Chunk 切分 -> 向量回填 -> 检索服务 -> 评测回归
```

这比单纯在业务表中追加若干 `ragSnippet` 字段更适合长期演进。

### 6.4 知识构建流程

RAG 构建由 `apps/backend/scripts/build-rag-db.ts` 承担，其流程可归纳为：

```text
1. 启动数据库环境并准备 schema
2. 收集公共知识、平台规则、机构资源与业务表样本
3. 标准化为 RagDocument
4. 按 chunk 策略切分为 RagChunk
5. 调用 embedding 网关生成向量
6. 写入知识库、文档、chunk 与构建批次记录
7. 支持增量同步与全量重建
```

该设计的重要意义在于：知识构建被视为一个可重复执行、可追踪、可对比结果的正式数据工程流程，而不是一次性的离线脚本。

### 6.5 检索流程设计

RAG 检索当前通过三个入口提供服务：

- 用户端入口：`/api/v1/app/ai/knowledge/search`
- 内部管理入口：`/api/v1/internal/agents/rag/search`
- Agent 工具入口：`searchKnowledgeBase`

检索流程遵循以下逻辑：

```text
查询归一化
 -> token 化
 -> 按可见域和知识类型筛选候选
 -> 词法召回
 -> 向量相似度重排
 -> 生成 excerpt、matchedTerms 与 citation
 -> 返回结果与 trace
```

其中，系统通过 `normalizeRagQuery`、`tokenizeRagQuery` 与 `scoreRagCandidate` 实现统一检索逻辑。当前策略并未引入外部向量数据库，而是在 PostgreSQL 中存储 chunk 与 embedding，并在应用层执行召回与重排。这种设计在现阶段兼顾了实现复杂度、可解释性与演进空间。

### 6.6 权限与隔离设计

RAG 的关键难点不是“能否检索出来”，而是“能否在正确授权范围内检索出来”。IntelliHealthCare 当前通过以下机制保证权限边界：

- App 侧默认只检索 `PUBLIC` 知识；
- 仅在显式传入 `includePrivate=true` 且授权校验通过时，联查 `USER_PRIVATE` 知识；
- App 侧不开放 `INSTITUTION_RESOURCE` 知识，避免机构侧资源被直接暴露给普通用户；
- 内部侧检索支持按 `ownerUserId`、`institutionId`、知识类型和可见域组合过滤；
- Agent 工具层同样要在调用前提供目标用户或机构上下文，不能越权读取私有知识。

这意味着 RAG 在设计上首先是授权系统的一部分，其次才是检索系统。

### 6.7 评测与质量闭环

RAG 的质量闭环由 `apps/backend/scripts/eval-rag.ts` 提供。评测过程包括：

- 加载固定数据集；
- 按案例定义的知识类型、可见域与目标对象执行检索；
- 计算匹配位置、`hit@1`、`hit@3`、`hit@5` 与 `MRR`；
- 将结果落入 `RagEvalRun` 与 `RagEvalCaseResult`；
- 在设定阈值下支持回归失败即中断。

这一设计说明 IntelliHealthCare 将 RAG 视为可验收的系统能力，而不是仅靠主观体验判断效果的实验性模块。

### 6.8 降级策略

为避免外部向量服务不可用导致系统整体失效，RAG 当前已实现降级机制：

- 未配置 embedding 网关时，系统回退到确定性占位向量；
- embedding 请求失败时，系统回退到 fallback embedding 或确定性向量；
- 检索仍保留词法召回链路，以保证基础可用性。

这一设计体现的是工程系统对“可运行性优先于算法理想态”的基本判断。

## 7. Hermes 多智能体框架设计

### 7.1 设计定位

Hermes 在 IntelliHealthCare 中被定义为“受控多智能体运行时”，而不是通用 AI 平台。它的职责是：

- 将来自用户端、后台端和内部系统事件的 AI 请求标准化为任务；
- 在统一的 Agent 注册表内完成路由、协作和任务分工；
- 在受控工具边界内访问健康、服务、报告、RAG 等领域能力；
- 将执行过程写入任务记录、审计记录和人工复核记录；
- 在高风险场景下，通过安全审查与人工兜底阻止越权或高风险自动执行。

因此，Hermes 的本质不是“多个 Agent 自由对话”，而是“统一控制面驱动的多 Agent 受控协作”。

### 7.2 设计原则

Hermes 的系统设计遵循以下原则：

- 单一控制面原则：所有任务首先进入统一控制面，而非各 Agent 自主抢占。
- 共享领域 Agent 原则：Agent 按稳定业务领域划分，不按前端页面碎片化划分。
- 受控协作原则：优先使用单 Agent 或串行协作，不采用无限轮自治讨论。
- 工具边界原则：Agent 不直接写数据库，只能通过受控工具访问业务上下文。
- 治理先行原则：高风险输出必须先过安全门禁，再进入人工复核或人工执行链路。
- 可追踪原则：任务、协调步骤、模型信息、工具调用摘要和人工决策都必须可回溯。

### 7.3 角色模型

Hermes 的统一蓝图当前定义了九个核心 Agent，并形成四类角色分工：

| 角色层 | Agent | 设计职责 |
| --- | --- | --- |
| 控制层 | `TaskOrchestratorAgent` | 统一任务标准化、路由与协作策略选择 |
| 交互层 | `AssistantConversationAgent`、`OperationsCopilotAgent` | 分别服务用户会话入口与后台运营摘要入口 |
| 领域层 | `HealthManagementAgent`、`CareCoordinationAgent`、`RiskOperationsAgent`、`DeviceOperationsAgent`、`ContentActivityOpsAgent` | 按健康、服务、风险、设备、内容域输出结构化结果 |
| 治理层 | `SafetyReviewAgent` | 对高风险内容进行统一安全门禁与人工复核触发 |

从实现角度看，当前 `AgentRegistry` 已注册上述 Agent，并兼容 `intent-router`、`report-summary-agent`、`service-recommendation-agent` 等旧别名。这说明 Hermes 已经不仅存在于蓝图文档中，而是具备统一注册、统一解析和统一执行的运行时基础。

### 7.4 任务生命周期设计

Hermes 的任务生命周期围绕 `AgentTask` 展开，可抽象为两种主链路。

第一条是内部异步链路：

```text
内部调用方
 -> 创建 AgentTask
 -> BullMQ 入队
 -> Worker 拉起任务
 -> Orchestrator 执行
 -> 安全审查/人工复核判定
 -> 回写结果、审计日志与复核工单
```

第二条是用户端同步链路：

```text
用户端 AI API
 -> AppAgentService
 -> 创建 AgentTask
 -> 同步调用 Orchestrator
 -> 回写结果
 -> 将结构化结果直接返回给用户端
```

这两条链路的共同点在于：无论同步还是异步，任务都必须先被持久化。这种设计使 Hermes 的执行不依赖瞬时内存状态，而是以任务为最小治理单元。

### 7.5 编排器设计

`AgentOrchestratorService` 是 Hermes 的核心。它的职责不是简单调用一个模型，而是完成以下工作：

- 根据 `AgentRegistry` 将请求解析到具体 Agent；
- 生成执行计划与 trace 基础框架；
- 在需要时触发多 Agent 协调执行；
- 在统一工具边界内调用报告、档案、指标、服务目录与 RAG 检索；
- 运行安全审查，并在必要时触发人工复核；
- 将最终结果封装为可审计的执行包。

这一设计保证 Hermes 具备“统一调度中枢”的性质，而不是每个 Agent 各自维护一套独立逻辑。

### 7.6 协同模式设计

Hermes 当前已经形成几种具有业务含义的协同模式。

#### 7.6.1 Assistant-First 模式

在用户助手场景中，系统优先由 `AssistantConversationAgent` 直接处理会话，仅在检测到涉及个人报告、个人健康摘要、服务推荐或预约推进时，才由编排器触发嵌套任务，再将下游结果整合回最终回复。

其逻辑可以表示为：

```text
用户消息
 -> AssistantConversationAgent
 -> 按需触发 report / health / service / booking 子任务
 -> 汇总领域洞察
 -> 生成最终会话回复
```

这种设计避免了“所有问题都先走复杂多 Agent 链路”的过度编排，有助于控制延迟和成本。

#### 7.6.2 健康理解增强模式

在健康摘要或报告解读场景中，系统先由 `HealthManagementAgent` 生成健康主域输出；若命中风险信号，再由 `RiskOperationsAgent` 补充风险分级和后续动作建议。

这使系统能够在“健康理解”与“风险运营”之间形成串行协作，而非将两者混为一个大 Prompt。

#### 7.6.3 风险补充背景模式

在风险任务中，系统先由 `RiskOperationsAgent` 完成风险等级、证据与处置建议，再按需调用 `HealthManagementAgent` 补充长期健康背景，以避免仅凭单一异常事件做判断。

这体现出 Hermes 协作设计的一个重要逻辑：风险判断不脱离健康背景，健康解释也不脱离风险处置语境。

#### 7.6.4 后台 Copilot 汇总模式

在后台运营摘要场景中，`OperationsCopilotAgent` 不直接假设拥有所有领域信息，而是先向健康、服务、风险、设备和内容域分别收集简报，再汇总成后台摘要输出。

该模式使后台 Copilot 成为“聚合者”而非“全知者”，从而维持领域边界清晰。

### 7.7 工具体系设计

Hermes 当前的核心工具包括：

- `ReportsTool`
- `HealthArchiveTool`
- `HealthMetricsTool`
- `ServiceCatalogTool`
- `RagRetrievalTool`

这些工具承载了 Hermes 与业务模块之间的正式边界。其设计原则是：

- 工具返回结构化数据，而不是任意拼接文本；
- 工具只暴露受控视角的数据，不暴露底层存储细节；
- 工具是 Agent 可调用的最小可信业务接口；
- Agent 不能绕开工具直接访问数据库或执行高风险写操作。

这意味着 Hermes 的智能行为始终运行在“工具授权域”内，而不是运行在“数据库完全访问域”内。

### 7.8 模型网关设计

Hermes 当前通过 `LlmGateway` 和 `EmbeddingGateway` 统一承接外部模型访问。

`LlmGateway` 负责：

- 主模型、轻量模型与 fallback 模型的选择；
- 严格结构化输出请求；
- 工具调用请求；
- provider 兼容适配与失败降级。

`EmbeddingGateway` 负责：

- embedding provider 选择；
- 主向量模型与 fallback 模型切换；
- 未配置密钥或请求失败时的确定性向量降级。

这一设计确保 Hermes 与具体模型服务商保持解耦，并能在外部依赖异常时维持系统基本可用。

### 7.9 治理与审计设计

Hermes 的治理链路由 `AgentGovernanceService` 负责落地。其设计不是简单记录日志，而是建立完整的任务治理闭环：

- `AgentTask` 记录任务生命周期；
- `AgentAuditLog` 记录创建、运行、成功、失败、重试和安全审查事件；
- `AgentHumanReview` 记录需要人工决策的高风险任务；
- `SafetyReviewAgent` 负责在最终输出前执行统一安全门禁。

因此，Hermes 的任务结果不只是“模型返回文本”，而是“模型输出 + trace + governance 元数据 + 审计事件”的组合结果。

### 7.10 风险控制结论

Hermes 的设计最终指向一个核心约束：AI 可以生成建议、摘要、排序和解释，但不能脱离业务规则直接成为最终执行者。尤其在健康与养老服务场景下，系统通过以下方式限制 AI 的越权：

- 对高风险任务标记 `humanReviewRequired`；
- 对内部接口施加后台身份、角色、来源 IP 与共享密钥限制；
- 对安全敏感输出进入 `SafetyReviewAgent`；
- 对高风险场景生成 `AgentHumanReview` 工单而不是直接写业务结果。

这保证 Hermes 是“业务增强引擎”，而不是“无边界自动决策引擎”。

## 8. Hermes 与 RAG 的协同设计

RAG 与 Hermes 在系统中的关系不是上下游偶然调用关系，而是“知识底座”与“智能执行层”的耦合设计。

### 8.1 协同逻辑

Hermes 负责决定“谁来执行、如何执行、是否需要协作、是否需要审查”；RAG 负责提供“执行所需的知识上下文与证据引用”。

二者协同关系如下：

```text
业务请求
 -> Hermes 编排器选择 Agent
 -> Agent 调用 RAG 工具检索知识
 -> 将检索结果压缩进 prompt
 -> 生成结构化输出
 -> 输出中保留 evidence / citation / trace
```

这意味着 RAG 并不直接替代 Agent 推理，也不直接替代业务规则判断，而是为 Agent 提供具备可见域约束和引用能力的知识上下文。

### 8.2 典型协同场景

在不同业务场景中，Hermes 与 RAG 的协同方式有所差异：

- 报告解读场景：`HealthManagementAgent` 结合报告上下文与健康知识，生成可解释摘要；
- 服务推荐场景：`CareCoordinationAgent` 结合服务目录知识和用户健康背景，输出推荐理由；
- 风险提醒场景：`RiskOperationsAgent` 结合风险规则、健康知识和用户历史，输出分级与处理建议；
- 用户助手场景：`AssistantConversationAgent` 在缺少明确个人上下文时优先使用公共知识与平台知识进行回答。

上述设计说明 Hermes 并不是单纯“调用 RAG 后发给模型”，而是在不同 Agent 的职责边界内，以不同方式消费知识。

## 9. 安全与治理设计

### 9.1 身份与作用域控制

系统采用两类核心作用域：

- `app`：用户端访问作用域；
- `admin`：后台访问作用域。

用户端与后台端分别通过不同登录接口获取 JWT，并由 `JwtAuthGuard` 在统一位置完成验证。后台内部 Agent 接口在此基础上再增加 `RolesGuard` 与 `InternalAccessGuard`，从而形成比普通后台接口更严格的访问控制。

### 9.2 内部智能体接口控制

内部 Agent 接口的访问条件包括：

- 必须具有后台 scope 的 JWT；
- 必须命中允许的来源 IP 段；
- 若配置了共享密钥，还必须提供 `X-Internal-Token`。

这一设计表明，Hermes 的内部治理接口并不被视为普通业务接口，而被视为平台内部高敏感控制面。

### 9.3 数据最小授权

系统在多个层面落实最小授权原则：

- App 侧默认不访问机构资源知识；
- 家属仅在绑定与授权成立时访问长者私有知识；
- Agent 工具只返回必要上下文，不暴露任意扩展数据；
- 内部治理接口按角色分配可见范围。

这使 AI 子系统与业务系统共享同一套隐私保护逻辑。

### 9.4 审计可追溯性

系统已建立如下可追溯链路：

- 请求级 `requestId`；
- 任务级 `AgentTask`；
- 审计级 `AgentAuditLog`；
- 风险级 `AgentHumanReview`；
- 检索级 `RagEvalRun / RagEvalCaseResult`。

这意味着对任一高风险输出，都可以追溯到其调用入口、任务类型、执行路径、是否触发安全审查、是否进入人工决策以及检索质量基线。

## 10. 演进策略与架构结论

### 10.1 当前演进阶段

从系统设计视角看，IntelliHealthCare 当前处于“统一底座已经形成，产品入口仍在深化”的阶段。其特点是：

- 用户端和后台端已具备稳定应用壳；
- 后端主要业务域、统一接口层和统一数据模型已形成；
- RAG 已形成正式数据模型、构建流程、检索入口与评测闭环；
- Hermes 已形成统一注册、统一编排、统一治理的可运行底座；
- 部分产品入口和蓝图能力仍在持续接入与细化。

这是一种健康的系统演进状态：底层机制先稳定，再让产品能力逐步上浮，而不是反过来先堆积入口再补基础设施。

### 10.2 总体结论

IntelliHealthCare 当前系统设计可概括为：

> 一套以模块化单体后端为业务核心、以单库多域为数据基础、以 RAG 为知识底座、以 Hermes 为受控多智能体运行时、以审计与人工复核为安全约束的智慧康养平台系统。

这一设计的关键价值不在于追求架构形式上的“先进”，而在于用统一、可控、可演进的方式，将健康数据、服务交易、内容互动与 AI 能力纳入同一系统逻辑中。对于养老健康场景而言，这种“业务统一性优先、智能增强受控、知识系统分层治理”的设计，比早期拆散平台或放任自治式 AI，更符合系统长期稳定演进的要求。
