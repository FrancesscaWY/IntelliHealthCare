# 架构说明

## 1. 为什么这样拆

智慧养老项目同时包含移动端用户场景和后台管理场景，页面多、参与成员多。如果直接把页面散落在一个应用里开发，会很快出现这些问题：

- 页面命名不统一，AI 生成代码时容易偏题。
- 成员互相改公共路由或入口文件，冲突很多。
- 新页面只有接到总应用里才能看，调试成本高。
- 页面缺少 mock 入口，别人接手时无法快速跑起来。

所以这里采用“页面目录即最小交付单元”的方式。

## 2. 核心约束

每个页面必须独立具备三部分：

1. `page.spec.json`
2. `page.mocks.ts`
3. `page.tsx`

这三个文件组合成统一页面模块：

- `spec` 负责描述页面是谁。
- `mocks` 负责描述页面如何单独测试。
- `tsx` 负责真实渲染。

这样不管是人写还是 Codex 写，最终都必须落到同一种结构上。

## 3. 双层测试入口

### 命令驱动

- `npm run dev:user`：启动用户端整体预览。
- `npm run dev:admin`：启动后台端整体预览。
- `npm run dev:page -- --app <app> --page <module/page>`：只启动一个页面。
- `npm run dev:all`：同时启动双端。

### Codex 提示词驱动

- `npm run prompt:page -- --app <app> --page <module/page>`

这个命令会把页面规范、目录、校验命令、禁止事项一起输出，团队成员可以直接复制给 Codex，降低 AI 生成风格不一致的问题。

## 4. 页面接入方式

应用入口通过 `import.meta.glob` 自动收集 `src/pages/**/page.tsx`。

这意味着：

- 新增页面不需要手工改总路由表。
- 只要页面目录正确，集成预览会自动出现。
- 成员之间主要冲突点被缩小到各自页面目录。

## 5. 状态管理策略

当前骨架先强调页面解耦，而不是过早上复杂全局状态。

建议约定：

- 页面独立开发阶段：优先使用 `page.mocks.ts` 提供本页数据。
- 模块联调阶段：再逐步替换为真实接口层。
- 真正共享的数据能力，后续可以沉淀到 `packages/` 下，而不是直接在应用中四处分散。

## 6. 命名建议

- 应用：`user-mobile`、`admin-console`
- 模块：`health-data`、`service-order`、`device-center`
- 页面：`overview`、`detail`、`list`、`edit`
- 页面 id：`<module>/<page>`

## 7. 团队协作守则

1. 不跨目录修改他人页面，除非明确协同。
2. 不在页面内直接写死外部依赖路径，先走页面契约。
3. 提交前必须至少完成一次单页预览和一次整体验证。
4. 所有新增页面都必须填写 `owner` 和 `prototype.reference`。
