# 智诊康养后端开发文档

## 1. 文档定位

本文档基于当前仓库在 `2026-04-20` 的实际状态重写，用来替换旧版以 `FastAPI / Python` 为核心的后端方案说明。

当前后端实现以以下内容为准：

- `apps/backend` 中已经落地的 `NestJS` 基础工程
- `apps/backend/prisma/schema.prisma` 中已经定义的数据库模型
- `docs/backend-architecture.md` 中确认的技术栈与架构边界
- `docs/hermes-agent-framework-requirements.md` 中确认的多 Agent 需求、分类与职责边界
- `docs/hermes-multi-agent-implementation.md` 中确认的 Agent 落地方式
- `docs/user-web-analysis-and-api.md` 中整理出的用户端 API 需求

本文档的原则只有三条：

1. 以当前仓库实现为准，不再沿用与代码不一致的旧技术栈描述。
2. 明确区分“已实现”“已建模/已预留”“待实现”三种状态。
3. 让后端开发、前后端联调和后续 Agent 接入都围绕同一套边界展开。

---

## 2. 当前后端定位

智诊康养当前后端不是微服务体系，而是一个放在 Monorepo 内的 `NestJS` 模块化单体：

```text
apps/user-web           用户端页面
apps/admin-web          后台端页面
        ↓
apps/backend            统一后端服务
        ↓
PostgreSQL              核心事务数据
Redis                   缓存/异步任务连接基础
MinIO                   对象存储
        ↓
后续接入 BullMQ Worker / Agent Runtime / RAG
```

这套后端承担三类职责：

1. 承接用户端与后台端的统一业务 API。
2. 承接健康档案、服务订单、报告、会话等核心业务数据。
3. 作为后续 `Hermes` 多智能体协同层的宿主，而不是另起一套独立 AI 平台。

当前阶段不采用微服务，原因很明确：

- 订单、档案、报告、会话、派单之间强耦合，先拆服务会放大事务和联调成本。
- 仓库已经统一在 `TypeScript` 栈下，后端继续使用同栈能降低协作成本。
- Agent 在当前项目里是业务增强层，不是独立主系统。

- `Agent` 相关能力目前停留在模块边界、环境变量和数据库模型阶段。

## 5. 全局运行约定

### 5.1 API 前缀

当前后端在 `main.ts` 中已经固定全局前缀：

```text
/api/v1
```

这意味着：

- 系统接口当前路径是 `/api/v1/system/*`
- 用户端业务接口后续应挂在 `/api/v1/app/*`
- 后台端业务接口后续应挂在 `/api/v1/admin/*`
- 仅内部使用的任务或回调接口，建议挂在 `/api/v1/internal/*`

### 5.2 响应结构

当前项目已经通过全局拦截器统一成功响应格式：

```json
{
  "code": 0,
  "message": "ok",
  "requestId": "uuid",
  "data": {}
}
```

这与 `docs/user-web-analysis-and-api.md` 中定义的通用响应结构一致，后续业务接口必须保持统一。

### 5.3 错误码映射

当前全局异常过滤器已经落地以下业务错误码映射：

| HTTP 状态码 | 业务码 |
| --- | --- |
| `400` | `40001` |
| `401` | `40003` |
| `403` | `40004` |
| `404` | `40400` |
| `409` | `40900` |
| `422` | `42200` |
| `500` | `50000` |

### 5.4 请求链路

当前项目已通过中间件统一生成和回传 `x-request-id`：

- 请求头带 `x-request-id` 时直接透传
- 未传时自动生成 UUID
- 响应头会回写同一个 `x-request-id`

这意味着后续日志、审计、Agent 任务回溯都应该复用同一个请求标识。

### 5.5 Swagger

当前已经可用的接口文档地址：

- Swagger UI：`/api/v1/docs`
- OpenAPI JSON：`/api/v1/docs/json`

### 5.6 健康检查

当前已经可用的系统接口：

- `GET /api/v1/system/health`
- `GET /api/v1/system/architecture`

其中 `system/health` 会检查：

- PostgreSQL 可达性
- Redis 可达性
- MinIO Bucket 配置状态

## 7. 数据库现状

当前数据库由 `Prisma + PostgreSQL` 驱动，已定义的核心枚举包括：

- `UserType`
- `UserStatus`
- `DeviceType`
- `DeviceStatus`
- `ServiceCategory`
- `OrderStatus`
- `WorkOrderStatus`
- `ReportType`
- `ConversationScene`
- `AgentTaskStatus`

### 7.1 已定义的核心模型

| 模型 | 用途 |
| --- | --- |
| `User` | 统一承接老人、家属、管理员、服务人员、机构负责人账号 |
| `Role` / `UserRole` | 承接后台 RBAC 与角色绑定 |
| `FamilyBinding` | 承接家属和老人之间的绑定与授权 |
| `HealthArchive` | 承接基础档案、病史、风险标签、长期记忆 |
| `Device` | 承接设备绑定、状态和最近一次同步数据 |
| `ServiceItem` | 承接服务目录、价格、可服务区域和知识片段 |
| `Order` | 承接预约订单、地址快照、联系人快照、AI 摘要 |
| `WorkOrder` | 承接派单结果、执行人、排班时间和派单建议 |
| `Report` | 承接体检报告、服务报告、康复报告与摘要 |
| `Conversation` | 承接会话主表 |
| `ConversationParticipant` | 承接会话参与人和未读计数 |
| `ConversationMessage` | 承接消息内容与发送人 |
| `AgentTask` | 承接 Agent 任务、输入负载、输出结果和状态 |

### 7.2 当前建模的特点

当前 Schema 采用了较多 `Json` 字段来承接暂未完全稳定的业务结构：

- `HealthArchive.baseProfile`
- `HealthArchive.medicalHistory`
- `HealthArchive.riskTags`
- `HealthArchive.longTermMemory`
- `Device.latestPayload`
- `ServiceItem.regionScope`
- `ServiceItem.ragSnippet`
- `Order.addressSnapshot`
- `Order.contactSnapshot`
- `Order.healthSummarySnapshot`
- `Order.aiSummary`
- `WorkOrder.agentDispatchSuggestion`
- `Report.summary`
- `Report.attachment`
- `Conversation.metadata`
- `ConversationMessage.content`
- `AgentTask.payload`
- `AgentTask.result`

这说明当前数据库策略不是一次性把所有字段定死，而是：

1. 先把核心主表稳定下来。
2. 对 AI 输出、地址快照、复杂报告、知识片段先用 `Json` 承接。
3. 等前端字段、运营流程和模型输出稳定后，再把高频结构抽成明确列或附表。

### 7.3 当前 Schema 已覆盖的业务域

目前已经有数据库基础的业务域：

- 账号与角色
- 家属绑定
- 健康档案
- 设备
- 服务目录
- 预约订单与工单
- 报告
- 会话消息
- Agent 任务

### 7.4 当前 Schema 尚未覆盖但 API 会需要的业务域

根据 `docs/user-web-analysis-and-api.md`，以下能力后续一定会需要扩表：

| 业务域 | 当前缺口 |
| --- | --- |
| 地址簿 | 当前只有 `Order.addressSnapshot`，没有独立地址表 |
| 健康指标历史 | 当前只有 `Device.latestPayload`，没有指标明细表和趋势表 |
| 用药/饮食/自测 | 当前没有对应实体 |
| 支付与退款 | 当前 `payments` 模块无表，订单里也未建支付单 |
| 售后/投诉/改约记录 | 当前只有订单状态，没有售后实体 |
| 消息通知中心 | 当前有会话表，但没有通知、模板、站内信聚合模型 |
| 内容资讯 | `content` 模块当前无表 |
| 社区帖子/活动 | `community` 模块当前无表 |
| 机构/服务人员/排班 | 当前工单只有名称字符串，没有机构和服务人员主数据 |
| 搜索历史/热词/定位城市 | 当前无独立实体 |
| 积分/优惠券/足迹 | 当前无独立实体 |

所以，后续业务开发不能只写 Controller 和 Service，还必须同步补齐 Prisma Schema。

这条链路能优先支撑：

- 用户登录
- 老人/家属绑定
- 健康档案查看
- 服务浏览与预约
- 订单创建

- 报告回填

## 10. Agent 与 Hermes 的落地方式

当前项目中，Agent 不应作为一个独立微服务系统先行建设，而应作为 `apps/backend/src/modules/agents` 内的受控能力落地。

### 10.1 当前已预留能力

仓库里已经为 Agent 准备了以下基础：

- `agents` 模块边界
- `AgentTask` Prisma 模型
- `AGENT_RAG_COLLECTION`
- `AGENT_LLM_BASE_URL`
- `AGENT_LLM_API_KEY`

### 10.2 当前尚未实现的关键能力

以下部分仍需开发：

- AgentTask 创建与状态流转服务
- BullMQ 队列与 Worker
- LLM Gateway
- 受控 Tool 层
- RAG 检索服务
- Prompt 版本管理
- 任务审计与成本记录

### 10.3 在当前项目中的正确接入方式

正确流程应为：

```text
业务模块创建 AgentTask
        ↓
写入数据库并投递队列
        ↓
Worker 拉起任务
        ↓
Agent Orchestrator 调用工具 / RAG / LLM
        ↓
结果写回 AgentTask 与业务表
        ↓
通知用户端或后台端
```

不建议做的事：

- 让 Agent 直接操作数据库
- 让多个 Agent 自由对话后自行落库
- 先做复杂自治，再补权限和审计

对当前项目来说，最适合先做的 Agent 场景是：

1. 报告摘要与报告解读增强
2. 服务推荐解释
3. 工单派单建议
4. 健康风险筛查提醒

## 14. 开发原则

1. 后端继续坚持 `NestJS` 模块化单体，不回退到 Python 方案。
2. 先做业务闭环，再扩张为全量业务域。
3. 先把 Prisma 模型补齐，再写大批业务接口。
4. 统一使用全局响应结构、错误码和 `x-request-id`。
5. Agent 只能作为受控业务能力接入，不能绕过业务模块直接落库。
6. BullMQ、JWT、WebSocket 虽已选型，但在代码真正落地前，不应在文档里写成“已实现”。
