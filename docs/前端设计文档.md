# IntelliHealthCare 前端设计文档

> 更新时间：`2026-04-25`
>
> 依据范围：`apps/user-web`、`apps/admin-web`、`packages/page-core`、`scripts/dev-user.mjs`、`scripts/build-user-web.mjs`、`scripts/create-page.mjs`

## 1. 文档目标

本文档用于说明 IntelliHealthCare 当前前端系统的设计思路、运行机制与工程约束，重点回答以下问题：

- 两套前端应用如何在同一 Monorepo 中协同演进；
- 用户端与后台端分别采用了什么运行时模型；
- 页面、组件、状态、鉴权与 API 调用是如何组织的；
- AI 能力在前端层如何接入；
- 当前前端工程体系如何保证页面可发现、可预览、可校验与可构建。

本文档描述的是当前仓库中已经实现的前端设计，而不是未来规划稿。

## 2. 前端总体定位

IntelliHealthCare 前端不是单一应用，而是两个独立工作区：

- `apps/user-web`：面向长者与家属的统一用户端；
- `apps/admin-web`：面向运营、医生、护理与机构管理人员的后台端。

两套前端共享以下基础特征：

- 技术栈统一为 `Vue 3 + TypeScript + Vite`；
- 页面资产均由 `pages.manifest.json` 显式登记；
- 页面组件通过 `import.meta.glob()` 动态发现与按需加载；
- 公共页面元数据与导航接口抽取到 `packages/page-core`；
- API 调用统一封装在 `src/shared/api/*` 中；
- 开发、构建、页面脚手架和结构校验由根级脚本统一调度。

但两套前端在运行时设计上并不完全相同：

- 用户端是 `vue-router + manifest` 模式；
- 后台端是 `单壳 + manifest + 内存页栈` 模式。

这一设计体现的是“统一页面协作模型，差异化运行时承载”的思路。

## 3. 前端总体架构

```text
Monorepo Root
├── apps/user-web
│   ├── app            用户端运行时、路由、页面加载
│   ├── pages          页面目录
│   ├── shared         API、鉴权、AI、共享组件
│   ├── components     通用页面组件
│   └── assets         静态资源
├── apps/admin-web
│   ├── app            后台运行时、页栈导航、工作台壳
│   ├── pages          页面目录
│   ├── shared         API、鉴权、项目元信息
│   ├── components     通用后台组件
│   └── assets         静态资源
└── packages/page-core
    ├── runtime.ts     页面 id、初始页、分组与底部导航
    └── types.ts       PageEntry、NavigationApi 等共享类型
```

从逻辑上看，前端可以分为五层：

- 应用壳层：`App.vue`、路由或页栈、顶层布局、Toast 与导航壳；
- 页面运行时层：页面清单、动态加载、页面导航 API、运行模式识别；
- 页面实现层：按业务域拆分的 `src/pages/**/Page.vue`；
- 共享能力层：鉴权、API、AI 状态、共享组件、项目元信息；
- 工程支撑层：脚手架、结构校验、单页预览、构建脚本。

## 4. 工作区设计

### 4.1 用户端 `apps/user-web`

用户端定位为长者与家属共享的一套 Web 应用。其主要业务域包括：

- 引导与登录；
- 首页、消息与个人中心；
- 家政护理、康复理疗、上门体检等服务流程；
- 健康数据、设备中心、用药与饮食管理；
- 健康档案、报告与历史资料；
- 内容资讯、疾病知识、社区互动；
- 智能助手、AI 报告解读、AI 服务推荐与 AI 知识检索。

当前用户端页面规模为 `98` 页，分组如下：

| 分组 | 数量 |
| --- | --- |
| `auth` | `4` |
| `community` | `5` |
| `content` | `6` |
| `diet-record` | `2` |
| `health` | `22` |
| `healthdocs` | `7` |
| `home` | `18` |

用户端采用 `vue-router` 作为实际路由容器，但并没有走传统的“手工维护路由表”模式，而是通过 manifest 自动生成路由项。这使用户端同时具备正式 URL 导航与页面资产登记能力。

### 4.2 后台端 `apps/admin-web`

后台端定位为桌面化运营工作台。其主要业务域包括：

- 登录与后台壳入口；
- 工作台总览与预约看板；
- 用户、报告与健康预警管理；
- 商品、服务人员、审核与工单管理；
- 订单、售后、评价与会话管理；
- 数据分析与系统配置。

当前后台端页面规模为 `42` 页，分组如下：

后台端当前未采用 `vue-router`，而是由顶层 `App.vue` 配合 `usePageNavigation.ts` 维护内存页栈。这种设计更适合当前后台原型深化与工作台式导航结构。

### 4.3 共享包 `packages/page-core`

`packages/page-core` 承载最小必要的前端共享运行时能力，而非完整 UI 框架。其职责包括：

- 定义 `PageEntry`、`NavigationApi`、`PageComponentProps` 等共享类型；
- 提供页面 id 归一化、初始页解析与页面分组函数；
- 提供用户端底部导航基础数据。

这种“轻共享”设计有两个优点：

- 避免共享层过重，降低两个前端工作区的耦合成本；
- 保证页面契约统一，同时允许用户端和后台端保留不同的运行方式。

## 5. 页面资产与运行时设计

### 5.1 页面清单机制

两套前端都将 `pages.manifest.json` 视为页面主数据源，而非把页面目录本身作为唯一事实来源。每个页面条目至少包含：

- `id`
- `title`
- `group`
- `route`
- `owner`
- `status`
- `summary`
- `folderPath`
- `modulePath`
- `mockPath`
- `legacySources`

这一设计的价值在于：

- 页面成为可管理、可检索、可校验的工程资产；
- 页面元信息集中存储，便于脚手架和校验工具消费；
- 页面目录与运行入口之间形成明确映射关系。

### 5.2 页面目录契约

前端页面目录的最小约束为：

```text
src/pages/<group>/<page>/
  Page.vue
  mock.ts
  README.md   # 可选
```

其中：

- `Page.vue` 负责页面结构、交互和局部状态；
- `mock.ts` 负责单页预览或开发中的本地调试数据；
- `README.md` 只在确有额外说明时保留，不是主数据来源。

### 5.3 动态加载机制

用户端和后台端都通过 `import.meta.glob("../pages/**/Page.vue")` 动态发现页面组件。

其共同流程为：

```text
读取 manifest
 -> 根据 pageId 解析组件路径
 -> 动态 import Page.vue
 -> 缓存已加载组件
 -> 页面壳为组件注入 pageEntry、manifest、navigation、showToast
```

这意味着页面不是一次性整包注册，而是按需装载。该设计适合当前大量页面、持续扩展页面目录的项目形态。

## 6. 用户端运行时设计

### 6.1 路由设计

用户端入口为 `src/main.ts`，挂载 `App.vue` 和 `router`。`src/app/router.ts` 基于用户端 manifest 动态生成路由表，并承担以下职责：

- 首页重定向；
- 页面 id 与 route 的双向映射；
- 登录校验与登录前目标页记录；
- 登录态丢失后的同步回跳；
- 页面标题设置与访问轨迹记录。

其设计特点是：

- 路由表来自页面清单，而不是手工散列维护；
- 路由层只负责导航与权限，不负责复杂业务状态；
- `PageHost.vue` 作为统一页面宿主，负责实际组件加载与错误兜底。

### 6.2 页面宿主设计

`PageHost.vue` 是用户端运行时的关键组件，其职责包括：

- 根据 `pageId` 解析当前页面条目；
- 读取组件缓存，按需加载页面模块；
- 控制页面加载态、超时态与错误态；
- 向页面组件注入统一 props。

这使业务页面可以专注于内容和交互，而无需重复处理导航、Toast 和 manifest 上下文。

### 6.3 导航抽象

虽然用户端使用 `vue-router`，但页面组件本身并不直接依赖原生路由 API，而是通过 `NavigationApi` 工作。`router-navigation.ts` 将 `push/replace/back` 包装为：

- `navigateTo`
- `redirectTo`
- `reLaunch`
- `navigateBack`
- `canGoBack`
- `getStack`

因此，页面层面对导航的认知是统一的页面 id 导航，而不是直接依赖 URL 细节。

## 7. 后台端运行时设计

### 7.1 应用壳设计

后台端入口为 `src/main.ts`，直接挂载 `App.vue`。顶层 `App.vue` 同时承担：

- 工作台整体布局；
- 主导航栏与二级侧边导航；
- 顶部搜索、通知与账号菜单；
- 当前页面组件装载；
- Toast 显示与局部交互状态维护。

后台端的壳层相较用户端更重，这是因为其本质是工作台应用，而非单纯页面容器。

### 7.2 页栈导航设计

后台端通过 `usePageNavigation.ts` 在内存中维护页面栈，而不是依赖浏览器 URL 路由。其设计过程为：

```text
解析 preferredPageId
 -> resolveInitialPage
 -> 构建 stack
 -> 通过 navigate/redirect/reLaunch 修改 stack
 -> 由 activePage 决定当前装载页面
```

这一模式使后台端具备两个特征：

- 适合单页预览和工作台内快速跳转；
- 允许顶部壳层在不切换 URL 的情况下保持完整状态。

### 7.3 工作台导航模型

后台端导航由两级组成：

- 一级导航：按业务主域划分，如工作台、数据分析、用户管理、服务管理、交易管理、系统设置、消息管理；
- 二级导航：根据当前主域动态展开对应页面列表。

这种导航模型与后台业务分组保持一致，有利于将页面组织方式与业务职责对应起来。

## 8. 状态管理设计

### 8.1 总体策略

当前前端没有引入 `Pinia`、`Vuex` 等全局状态中心。状态管理采取“局部响应式状态 + 少量模块级共享状态 + 浏览器存储持久化”的策略。

这一设计符合当前项目状态：

- 页面多但跨页面全局状态不复杂；
- 登录态、AI 会话态和少量偏好配置需要持久化；
- 更需要降低心智负担，而不是引入完整状态管理框架。

### 8.2 局部状态

大多数页面交互状态在页面组件中通过 `ref`、`computed`、`watch` 等组合式 API 管理。这类状态通常包括：

- 当前 Tab；
- 表单输入；
- 局部筛选条件；
- 加载中与错误信息；
- 弹窗、抽屉和面板开关状态。

### 8.3 共享状态

当前共享状态主要集中在三个类别：

- 登录会话状态；
- Toast 队列；
- 用户端 AI 相关状态。

用户端的 AI 状态 `src/shared/ai/state.ts` 维护：

- 助手历史会话；
- 当前激活会话；
- 服务推荐结果；
- 报告分析结果；
- 选中的报告；
- 助手入口意图。

这些状态通过模块级 `ref` 与 `localStorage` 同步，形成轻量持久化状态层。

### 8.4 Toast 设计

用户端和后台端都提供 `useToastQueue()`，但实现策略略有差异：

- 用户端使用模块级单例队列，使顶层 Toast 能跨页面共享；
- 后台端在应用壳内创建局部队列，更贴合单壳工作台状态。

这说明两个前端虽然共享能力目标一致，但仍保留了符合自身壳层模型的实现差异。

## 9. 鉴权与访问控制设计

### 9.1 用户端鉴权

用户端登录态由 `src/shared/auth/session.ts` 管理，存储在 `localStorage` 中，主要包含：

- `accessToken`
- `refreshToken`
- `tokenType`
- `expiresIn`
- 当前用户基础信息

路由访问控制由 `src/shared/auth/navigation.ts` 和 `router.beforeEach()` 共同实现：

- 公共页可直接访问；
- 受保护页面在未登录时跳转到登录页；
- 登录前目标页会写入 `sessionStorage`；
- 登录成功后根据实名状态与待跳转页面决定落点。

### 9.2 后台端鉴权

后台端同样通过共享模块管理会话，但支持两种持久化策略：

- `sessionStorage`：默认短期会话；
- `localStorage`：显式持久化登录。

后台端 `usePageNavigation.ts` 在导航时执行鉴权判断：

- 未登录访问受保护页面时跳回 `auth/login`；
- 登录后优先恢复登录前目标页，否则进入默认首页 `dashboard/overview`；
- 会话清除时，如当前页面需要登录，则强制回到登录页。

### 9.3 权限设计结论

当前前端权限控制以“会话存在性 + 页面粒度登录要求”为主，并未在前端实现复杂角色矩阵。更细粒度的角色权限控制主要依赖后端接口校验。这种设计符合当前阶段的职责划分：前端负责基本入口控制，后端负责最终权限判定。

## 10. API 接入设计

### 10.1 API 客户端抽象

两套前端均在 `src/shared/api/client.ts` 中封装统一的 `request<T>()` 方法，负责：

- 解析 `VITE_API_BASE_URL`；
- 开发环境下优先走 `/api/v1` 代理；
- 自动注入 `Authorization`；
- 自动处理 JSON body；
- 解析统一响应包 `ApiEnvelope<T>`；
- 将错误封装为 `ApiClientError`；
- 在鉴权错误时清理本地会话。

这使页面与业务模块调用层面不直接接触 `fetch` 细节，从而形成一致的请求协议。

### 10.2 模块化 API 组织

用户端与后台端都按业务域拆分 API 文件。

用户端主要包括：

- `auth.ts`
- `ai.ts`
- `content.ts`
- `files.ts`
- `messaging.ts`
- `orders.ts`
- `payments.ts`
- `reports.ts`

后台端主要包括：

- `auth.ts`
- `analytics.ts`
- `catalog.ts`
- `dashboard.ts`
- `elders.ts`
- `messaging.ts`
- `orders.ts`
- `reports.ts`
- `system.ts`
- `work-orders.ts`

这体现的是“前端 API 模块按业务域组织，而非按页面组织”的设计。

### 10.3 联调与代理策略

两套前端 Vite 配置都提供了 `/api/v1` 代理，默认目标为：

```text
http://server.mctown.online:8190
```

其优点包括：

- 本地开发时避免浏览器跨域问题；
- 支持通过 `IHC_BACKEND_TARGET` 切换后端目标；
- 生产或部署态可通过环境变量覆盖 API 根地址。

用户端额外处理了 HTTPS 页面加载时的 mixed-content 回退，避免页面本身为 HTTPS 时直接访问 HTTP API 被浏览器阻断。

## 11. AI 前端接入设计

### 11.1 用户端 AI 入口

用户端已经具备明确的 AI 前端接入层，主要位于：

- `src/shared/api/ai.ts`
- `src/shared/ai/runtime.ts`
- `src/shared/ai/state.ts`
- `src/shared/ai/voice.ts`
- `src/shared/ai/components/*`

当前 AI 前端能力包括：

- 智能助手会话创建、消息列表与发送；
- AI 服务推荐；
- AI 预约预填；
- AI 健康摘要；
- AI 指标解释；
- AI 报告解读与后续建议；
- AI 风险提醒；
- AI 知识检索；
- 语音录制与可选语音转写。

### 11.2 AI 状态与页面协作

AI 能力并非只停留在 API 调用层，而是通过 `shared/ai/state.ts` 持久化为跨页面可复用状态。这使以下场景成为可能：

- 从首页或服务页发起 AI 推荐，再在详情页复用结果；
- 从报告页进入 AI 解读页，复用选中的报告上下文；
- 将文本草稿或语音输入意图跨页面传递到助手会话页。

因此，AI 前端设计已经从“单接口联调”进入“页面间协同消费 AI 结果”的阶段。

### 11.3 后台端 AI 现状

后台端当前还没有与用户端对等的独立 AI 状态层，但已存在可承接后台智能摘要与运营分析结果的页面壳与业务 API 结构。后续若接入后台 Copilot，更适合沿用“业务 API + 页面模块”的方式，而不是再平行创建一套完全独立的 AI 前端框架。

## 12. 组件与样式设计

### 12.1 组件组织

组件层当前采用三类组织方式：

- `src/components`：面向当前工作区的通用组件；
- `src/shared/components`：用户端共享能力组件；
- 页面目录内局部组件：仅服务单页面或单业务域。

用户端典型组件包括：

- `BottomTabBar.vue`
- `ToastViewport.vue`
- `AuthVerificationBanner.vue`
- AI 历史会话面板等。

后台端典型组件包括：

- `PagePlaceholder.vue`
- `ToastViewport.vue`
- 工作台壳中的导航与通知结构。

### 12.2 样式策略

两套前端均在 `src/app/base.css` 中定义全局基础样式，再由页面和组件使用 `scoped style` 实现局部样式封装。当前设计没有引入第三方样式系统或原子化样式框架，而是以组件局部样式为主。

这种策略的特点是：

- 易于快速迭代页面；
- 降低样式系统引入成本；
- 但在页面规模继续增长时，需要额外关注设计语言统一性。

## 13. 工程协作与构建设计

### 13.1 页面脚手架

项目通过根级脚本 `scripts/create-page.mjs` 生成前端页面脚手架。其职责包括：

- 创建页面目录；
- 生成 `Page.vue` 与 `mock.ts`；
- 可选创建 `README.md`；
- 自动向 `pages.manifest.json` 写入页面条目。

这一设计保证新页面进入仓库时即满足基本目录契约。

### 13.2 结构校验

`scripts/validate-workspace.mjs` 在开发和构建前执行工作区校验，主要检查：

- 页面 id 是否重复；
- manifest 中登记的页面目录是否存在；
- 已实现页面是否包含 `Page.vue` 与 `mock.ts`。

这意味着前端工程不是“目录存在即可”，而是“目录、清单和运行入口必须一致”。

### 13.3 单页预览与整站预览

`scripts/dev-user.mjs` 支持两种运行模式：

- `app`：整站模式；
- `page`：单页预览模式。

该脚本会：

- 根据目标工作区加载 manifest；
- 校验目标页面是否存在；
- 自动处理端口占用；
- 注入 `VITE_IHC_MODE` 和 `VITE_IHC_PAGE_ID`；
- 输出本地与局域网预览地址。

这一设计直接服务于页面级协作和高频 UI 联调。

### 13.4 构建设计

两套前端都使用 Vite 构建，并输出到仓库根级 `dist/`：

- 用户端输出：`dist/user-web`
- 后台端输出：`dist/admin-web`

根级 `scripts/build-user-web.mjs` 在构建前会先执行工作区结构校验，再触发对应工作区的正式构建，从而将“结构正确性”前置为构建前置条件。

## 14. 当前前端设计结论

IntelliHealthCare 当前前端设计可以概括为：

> 以页面清单为中心、以动态页面装载为运行基础、以双应用差异化运行时承载不同业务场景、以轻共享包维持契约统一、以模块化 API 和浏览器持久化状态承接业务与 AI 能力的一套前端体系。

该体系的关键价值不在于引入大量框架，而在于：

- 用页面清单统一管理大规模页面资产；
- 用轻共享运行时保持双应用协作一致性；
- 用简单直接的状态和鉴权方案降低实现复杂度；
- 用清晰的 API 模块边界和 AI 接入层支撑后端能力持续演进。

从当前代码形态来看，这是一套强调工程可控、页面协作效率和业务快速落地的前端设计，而不是追求重平台化或重框架化的前端架构。
