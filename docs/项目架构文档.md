# IntelliHealthCare 系统架构文档

> 更新时间：`2026-04-25`
>
> 事实依据：`apps/user-web`、`apps/admin-web`、`apps/backend`、`packages/page-core`、`scripts`、`apps/backend/prisma/schema.prisma`
>
> 编写原则：只描述当前仓库中已经实现、或可以直接从代码稳定推导出的架构事实，不把规划态能力写成现状。

## 1. 文档目标

本文档用于统一说明 IntelliHealthCare 当前代码库的系统架构，覆盖以下四个层面：

- 业务与应用架构：系统由哪些应用组成，分别服务哪些角色。
- 技术与实现架构：前端、后端、数据库、缓存、对象存储和 AI 子系统如何协同。
- 工程协作架构：Monorepo、页面清单、脚手架、校验脚本和测试脚本如何组织团队开发。
- 运行与部署架构：本地依赖、启动方式、默认端口、开发回退机制和外部依赖边界。

本文不展开接口逐条说明；接口明细应以 `docs/backend-api-manual.md` 为准。

## 2. 架构结论

IntelliHealthCare 当前采用的是一套基于 `npm workspaces` 的全栈 Monorepo。系统不是多仓库拼装，也不是微服务集群，而是“两个前端应用 + 一个 NestJS 模块化单体后端 + 一套共享基础设施”的交付形态。

系统的几个关键结论如下：

- 前端是双应用架构：`apps/user-web` 面向长者与家属，`apps/admin-web` 面向运营、医生、护理和机构后台人员。
- 后端是模块化单体：所有业务域统一收敛在 `apps/backend` 中，通过模块划分边界，但仍运行在同一个 NestJS 进程内。
- 数据层是单数据库模式：后端统一通过 Prisma 访问 PostgreSQL，没有按业务域拆分数据库。
- 基础设施是轻量集中式：Redis 负责队列与运行时连接，MinIO 负责对象存储，Swagger 负责 API 可发现性。
- AI 不是外挂系统：Agent、RAG、人工复核和审计链路都直接内嵌在后端模块内。
- 当前在线交互以 HTTP/REST 为主：代码中没有实际启用的 WebSocket 网关，也没有事件总线或独立流处理平台。

## 4. 系统上下文

```text
长者 / 家属
    |
    v
apps/user-web  ------------------------------+
                                             |
运营 / 医生 / 护理 / 机构后台                 |
    |                                        |
    v                                        v
apps/admin-web  -------------------->  apps/backend (NestJS)
                                      /app  /admin  /system  /internal/agents
                                                |
                          +---------------------+----------------------+
                          |                     |                      |
                          v                     v                      v
                    PostgreSQL             Redis + BullMQ           MinIO
                          |
                          +--> Agent Runtime / RAG / Audit / Human Review
                          |
                          +--> 可选外部 LLM / Embedding 网关
```

系统中的主要业务角色来自 `UserType` 枚举：

- `ELDER`：长者用户
- `FAMILY`：家属用户
- `ADMIN`：后台管理员
- `STAFF`：服务或护理人员
- `ORG_MANAGER`：机构管理角色

## 6. 应用架构

### 6.1 用户端 `apps/user-web`

用户端采用 `Vue 3 + TypeScript + Vite`，当前已经是基于 `vue-router` 的真实路由应用，而不是纯粹的内存页栈。

它的核心实现特点如下：

- 入口为 `src/main.ts`，挂载 `App.vue` 和 `router`。
- `src/app/router.ts` 根据 `pages.manifest.json` 动态生成路由表。
- `src/app/page-loader.ts` 使用 `import.meta.glob("../pages/**/Page.vue")` 按页面目录动态装载组件。
- `src/app/page-manifest.ts` 负责页面 id、route、manifest 的映射。
- 登录态通过 `src/shared/auth/session.ts` 持久化到 `localStorage`。
- API 通过 `src/shared/api/client.ts` 直接请求后端 `/api/v1`，没有单独 BFF。

当前用户端页面按 manifest 分组如下：

| 分组 | 数量 |
| --- | --- |
| `auth` | `4` |
| `community` | `5` |
| `content` | `5` |
| `diet-record` | `2` |
| `health` | `22` |
| `healthdocs` | `7` |
| `home` | `17` |
| `onboarding` | `1` |
| `orders` | `10` |
| `service` | `23` |

用户端的典型架构链路如下：

```text
Router -> PageHost / Page.vue -> shared/api/* -> /api/v1/app/*
```

用户端 AI 接入也已经落地在前端：

- `src/shared/ai/runtime.ts` 负责组合式调用 AI 服务推荐、报告解读、健康摘要、知识检索等接口。
- `src/shared/ai/state.ts` 维护对话历史、推荐结果、报告分析状态。
- `src/shared/ai/voice.ts` 使用浏览器 `MediaRecorder` 和可选 `SpeechRecognition` 实现语音输入。

### 6.2 后台端 `apps/admin-web`

后台端同样采用 `Vue 3 + TypeScript + Vite`，但其导航模式与用户端不同。

当前后台端不是 `vue-router` 多路由站点，而是 manifest 驱动的单壳应用：

- 入口为 `src/main.ts`，直接挂载 `App.vue`。
- `src/app/usePageNavigation.ts` 在内存中维护页面栈，实现 `navigateTo / redirectTo / reLaunch / navigateBack`。
- `src/app/page-registry.ts` 同样通过 `import.meta.glob` 动态加载页面组件。
- `src/app/resolve-config.ts` 负责识别整站模式与单页预览模式。
- 登录态由 `src/shared/auth/session.ts` 管理，支持 `sessionStorage` 或 `localStorage`。
- API 通过 `src/shared/api/client.ts` 直接访问后端 `/api/v1/admin/*`。

当前后台端页面按 manifest 分组如下：

| 分组 | 数量 |
| --- | --- |
| `analytics` | `10` |
| `auth` | `1` |
| `community` | `1` |
| `content` | `3` |
| `dashboard` | `11` |
| `device` | `1` |
| `elder` | `4` |
| `health` | `1` |
| `service` | `5` |
| `staff` | `1` |
| `system` | `4` |

后台端当前更像“运营工作台壳层 + 页面组件目录”，而不是以 URL 路由为中心的后台管理框架。

### 6.3 前端共享层 `packages/page-core`

`packages/page-core` 当前非常轻，只承载最基础的页面运行时契约：

- `src/types.ts`：页面条目、导航接口、页面组件 props、底部栏类型。
- `src/runtime.ts`：页面 id 归一化、首页解析、页面分组、状态元信息。

这意味着当前前端共享策略是“最小共享”：

- 共享页面元数据和轻量运行时。
- 不共享复杂状态管理。
- 不引入统一 UI 框架或全局 store。

当前代码中没有 `Pinia`、`Vuex` 等全局状态中心。

### 6.4 工程脚本层 `scripts`

根级脚本承担“多应用统一入口”的职责，而不是承载业务逻辑。

关键脚本包括：

- `scripts/dev-user.mjs`：启动用户端或后台端开发服务，支持整站和单页预览。
- `scripts/build-user-web.mjs`：构建前执行 workspace 校验，再触发对应前端构建。
- `scripts/validate-workspace.mjs`：校验页面目录、`Page.vue`、`mock.ts` 与 manifest 的一致性。
- `scripts/create-page.mjs`：按约定生成页面目录、`Page.vue`、`mock.ts` 和 manifest 条目。
- `scripts/backend-smoke-*.mjs`：后端冒烟与回归脚本。

这里反映出一个重要工程结论：前端协作单元不是“路由文件”，而是“manifest 中登记的页面目录”。

## 7. 后端架构

### 7.1 架构模式

后端 `apps/backend` 采用 `NestJS + TypeScript`，当前是标准的模块化单体：

- 一个进程
- 一个 API 前缀
- 一个数据库
- 多个业务模块
- 少量共享基础设施模块

它不是以下形态：

- 不是微服务集群
- 不是按域拆库拆服务
- 不是独立 BFF + 独立 AI 网关 + 独立 CMS 的组合

### 7.2 运行时主装配

`src/app.module.ts` 当前共装配 `20` 个模块，其中 `3` 个基础设施模块、`17` 个系统/业务模块：

### 7.3 路由分层

后端当前采用统一前缀 `/api/v1`，其下分成四类路由面：

| 路由层 | 前缀 | 用途 |
| --- | --- | --- |
| 系统层 | `/api/v1/system/*` | 健康检查、架构摘要、系统可发现性 |
| 用户端 | `/api/v1/app/*` | 长者/家属业务接口与 AI 接口 |
| 后台端 | `/api/v1/admin/*` | 运营、机构、分析与配置接口 |
| 内部治理层 | `/api/v1/internal/agents/*` | Agent 任务、治理、RAG 管理接口 |

当前后端控制器共 `19` 个，HTTP 接口共 `262` 个。

### 7.4 横切机制

后端的横切能力已形成统一约束：

- `RequestContextMiddleware`：为每个请求生成或透传 `x-request-id`。
- `ApiResponseInterceptor`：把成功响应统一封装为 `{ code, message, requestId, data }`。
- `AllExceptionsFilter`：把异常统一映射为业务错误码。
- `ValidationPipe`：全局启用 DTO 校验、转换和白名单过滤。
- `JwtAuthGuard`：校验 Bearer Token 并向请求注入 `user`。
- `RolesGuard`：按角色元数据做 RBAC 校验。
- `InternalAccessGuard`：对内部 Agent 接口叠加 `admin` scope、来源 IP 和可选共享密钥校验。

### 7.5 数据访问风格

当前后端没有额外抽一层 Repository 框架，主要模式是：

- 控制器负责协议层和 DTO。
- Service 负责业务组装。
- Service 直接依赖 `PrismaService` 访问数据库。

这是典型的“业务模块 + 共享 ORM”风格。当前仅有少量显式模块依赖，例如 `FamilyModule` 引用 `UsersModule`；大部分模块之间通过数据库与共享工具协同，而不是通过复杂的服务调用图协同。

## 8. 数据架构

### 8.1 数据存储形态

当前系统的数据底座是：

- `PostgreSQL`：主业务数据库
- `Prisma`：唯一正式 ORM
- `Redis`：队列与运行时连接
- `MinIO`：对象存储

系统没有以下结构：

- 没有独立搜索引擎集群
- 没有消息中间件集群
- 没有专用 OLAP 仓库
- 没有按业务域拆开的多库体系

### 8.2 Prisma 模型分区

`schema.prisma` 当前共有 `66` 个模型，可以按职责划分为五组：

| 分区 | 代表模型 | 说明 |
| --- | --- | --- |
| 身份与组织 | `User`、`Role`、`UserRole`、`FamilyBinding`、`Institution`、`Staff` | 账号、角色、家属关系、机构与人员 |
| 健康与档案 | `HealthArchive`、`Device`、`HealthMetricRecord`、`HealthAlert`、`Medication`、`Report` | 健康档案、设备、指标、风险与报告 |
| 服务与交易 | `ServiceItem`、`Order`、`WorkOrder`、`PaymentOrder`、`RefundOrder`、`AfterSaleRequest` | 服务目录、订单履约、支付、退款与售后 |
| 内容与互动 | `Article`、`Lecture`、`DiseaseKnowledge`、`CommunityPost`、`Activity`、`ConversationMessage`、`Notification` | 资讯、讲堂、社区、活动、消息、通知 |
| AI 与知识库 | `AgentTask`、`AgentHumanReview`、`AgentAuditLog`、`RagKnowledgeBase`、`RagDocument`、`RagChunk` | Agent 治理、RAG 数据、评测与审计 |

### 8.3 数据边界结论

当前数据架构的本质是“单库多域”：

- 所有核心域共享同一个 PostgreSQL 实例。
- 边界主要通过模块、模型和路由分层体现。
- 尚未引入 CQRS、Event Sourcing 或独立读模型系统。

## 9. AI 与 RAG 架构

### 9.1 模块定位

`apps/backend/src/modules/agents` 是当前系统的 AI 子系统宿主，不是独立部署的 AI 平台。

它当前承担四类职责：

- Agent 定义、注册与路由
- LLM / Embedding 网关调用
- RAG 检索与评测
- 审计、人工复核和内部治理接口

### 9.2 核心组件

`AgentsModule` 当前包含以下关键部件：

- `AgentRegistry`：管理 Agent 定义与别名映射
- `AgentTaskService`：创建、查询、重试和更新 AgentTask
- `AgentDispatchService`：向 BullMQ 队列投递任务
- `AgentTaskProcessor`：消费队列并执行任务
- `AgentOrchestratorService`：核心编排器，负责路由、工具调用、协调链路和失败封装
- `AppAgentService`：面向用户端 AI 接口的服务层
- `RagKnowledgeService` / `RagEvaluationService`：知识检索与评测
- `LlmGateway` / `EmbeddingGateway`：统一模型与向量网关
- `ReportsTool`、`HealthArchiveTool`、`HealthMetricsTool`、`RagRetrievalTool`、`ServiceCatalogTool`：受控工具层

### 9.3 两种执行模式

当前 Agent 执行存在两种入口模式。

第一种是内部异步任务模式：

```text
/internal/agents/tasks
    -> AgentTask 入库
    -> BullMQ 入队
    -> AgentTaskProcessor 消费
    -> AgentOrchestratorService 执行
    -> 结果/trace/审计回写
```

第二种是用户端同步执行模式：

```text
/app/ai/*
    -> AppAgentService
    -> AgentTask 入库
    -> 同步调用 AgentOrchestratorService
    -> 持久化结果后直接返回前端
```

也就是说，用户端 AI 并不是“只算内存结果”，而是同样会留下 `AgentTask` 记录。

### 9.4 治理链路

AI 子系统当前已内建治理能力：

- `AgentTask`：任务生命周期持久化
- `AgentAuditLog`：任务审计日志
- `AgentHumanReview`：人工复核工单
- 高风险输出会进入安全复核链路
- `trace` 中会记录协调步骤、模型信息和工具调用摘要

### 9.5 RAG 检索

RAG 已经不是概念层设计，而是后端内建能力。

当前能力包括：

- `RagKnowledgeBase`、`RagDocument`、`RagChunk` 数据模型
- App 侧知识检索：`/api/v1/app/ai/knowledge/search`
- 内部管理侧检索与评测：`/api/v1/internal/agents/rag/*`
- 离线构建脚本：`apps/backend/scripts/build-rag-db.ts`
- 回归评测脚本：`apps/backend/scripts/eval-rag.ts`

当前检索策略是：

- 先做词法召回
- 再结合 embedding 余弦相似度重排
- 未配置真实 embedding 网关时回退到确定性占位向量

### 9.6 外部 AI 依赖边界

LLM 与 Embedding 当前通过环境变量选择网关：

- `deepseek`
- `openrouter`
- `openai-compatible`
- `mock`

这带来两个明确结论：

- AI 运行时依赖是可插拔的，不和单一厂商强耦合。
- 未配置真实 Key 时系统仍可启动，但会回退到确定性输出或占位向量，适合开发联调，不适合生产质量要求。

## 10. 文件与媒体架构

文件处理当前采用“预签名上传 + 元数据回填”的方式：

```text
前端
  -> POST /app/files/presign 或 /admin/files/presign
  -> 直接上传到 MinIO
  -> POST /files/complete
  -> 后端持久化 FileAsset
```

`StorageService` 同时负责：

- 确保 bucket 存在
- 生成预签名上传 URL
- 校验对象存在
- 生成对象公开访问 URL

这说明当前媒体流量并不经后端二进制转发，而是以后端签发权限、对象存储承载文件内容。

## 11. 运行与部署架构

### 11.1 本地基础设施

`docker-compose.backend.yml` 当前编排了三项依赖：

- PostgreSQL `16`
- Redis `7`
- MinIO

默认端口如下：

| 组件 | 端口 |
| --- | --- |
| 用户端 | `5173` |
| 后台端 | `5174` |
| 后端 | `8190` |
| PostgreSQL | `5432` |
| Redis | `6379` |
| MinIO API | `9000` |
| MinIO Console | `9001` |

### 11.2 开发态数据库回退

后端在开发环境下提供了一个很有特点的回退机制：

- 如果 `DATABASE_URL` 不可连通
- 且 `DATABASE_DEV_FALLBACK_ENABLED=true`
- 后端会自动启动嵌入式 PostgreSQL（基于 `PGlite`）
- 自动执行 migration / seed

因此当前开发启动不是“数据库不可达就直接失败”的硬依赖模式，而是“优先连真实库，失败时回退嵌入式数据库”的增强模式。

### 11.3 启动链路

后端启动主流程如下：

```text
bootstrapDatabase()
    -> 读取 env
    -> 检查 DATABASE_URL
    -> 必要时启用嵌入式 PostgreSQL
    -> 启动 NestJS
    -> 注册 CORS / 静态资源 / 全局前缀 / 校验 / 过滤器 / 拦截器 / Swagger
```

## 12. 工程协作架构

### 12.1 开发命令入口

根级 `package.json` 是所有工作区的统一入口，核心命令包括：

- `dev:user`、`dev:admin`、`dev:backend`
- `build:user`、`build:admin`、`build:backend`
- `check:user`、`check:admin`、`check:backend`
- `test:backend:*`
- `db:*:backend`

### 12.2 页面协作模型

当前前端研发流程不是手写路由优先，而是 manifest 驱动优先：

- 页面必须登记在 `pages.manifest.json`
- 页面目录至少包含 `Page.vue` 和 `mock.ts`
- 脚手架自动生成页面模板
- 构建和开发启动前会执行结构校验

这让页面成为稳定的协作单元，也使“单页预览”成为正式工程能力，而不是临时开发技巧。

### 12.3 测试与质量保障

后端当前已有三类质量入口：

- 单元测试：`apps/backend/test/unit/*`
- 集成测试：`apps/backend/test/integration/*`
- 冒烟与回归脚本：根级 `scripts/backend-smoke-*.mjs`

RAG 子系统还有专门的离线评测入口：

- `npm run db:build-rag:backend`
- `npm run db:rebuild-rag:backend`
- `npm run db:eval-rag:backend`

## 13. 当前架构边界

为了避免后续文档和实现再次错位，需要明确以下边界：

- 当前后端是模块化单体，不是微服务。
- 当前用户端已经采用 `vue-router`，后台端没有采用 `vue-router`。
- 当前前端没有引入 `Pinia` 等全局状态中心。
- 当前前后端主交互方式是 HTTP/REST，没有启用实际 WebSocket 网关。
- 当前 AI 运行时内嵌在后端，不是独立 AI 平台。
- 当前数据库是单 PostgreSQL 实例，没有按域拆库。
- 当前后台多个管理域由 `AdminModule + AdminService` 集中承载，尚未继续拆成更细后台子模块。

## 14. 总结

IntelliHealthCare 当前最准确的架构定义是：

> 一套以 `npm workspaces` 管理的全栈 Monorepo，包含双前端应用、一个 NestJS 模块化单体后端、单 PostgreSQL 数据底座、Redis/BullMQ 队列、MinIO 对象存储，以及内嵌于后端的 Agent/RAG/治理子系统。

从工程实现上看，这套架构的重点不是“大而全的技术拼盘”，而是把用户端、后台端、健康数据、服务交易、内容社区和 AI 能力收敛到同一业务底座中，再通过 manifest、脚手架、统一 API 约定和共享运行时维持协作效率。
