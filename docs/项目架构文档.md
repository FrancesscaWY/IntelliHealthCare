# IntelliHealthCare 项目架构文档

> 本文基于当前仓库实现整理，更新时间为 `2026-04-24`。本文描述的是“代码里已经落地的架构”，不是目标蓝图或早期规划稿。

## 1. 架构结论

IntelliHealthCare 当前采用的是一套 **`npm workspaces` 管理的全栈 Monorepo**，核心交付单元不是多个拆散仓库，而是以下 4 个工作区：

- `apps/user-web`：面向长者与家属的用户端 Web 应用
- `apps/admin-web`：面向运营、医生、护理与机构管理人员的后台工作台
- `apps/backend`：统一后端服务，采用 `NestJS` 模块化单体
- `packages/page-core`：前端页面运行时、类型定义与轻量共享工具

当前项目的真实架构形态可以概括为：

- 前端是 **双应用、同技术栈、同页面装配模式**
- 后端是 **单服务、多业务模块、统一 API 前缀**
- 数据与基础设施是 **`PostgreSQL + Prisma + Redis/BullMQ + MinIO`**
- AI 能力已经不是外部概念，而是后端内的 **Hermes Agents Runtime + RAG 检索链路**
- 仓库中保留了 `legacy/miniprogram-user`，但它是迁移参考资产，不是当前主交付目标

需要特别说明：

- 当前仓库使用的是 `npm workspaces`，不是 `pnpm workspace`、`Turborepo` 或 `Nx`
- 前端当前没有引入 `Vue Router`、`Pinia` 和 SSR，而是使用页面清单 + 自定义导航栈
- 后端当前是 **模块化单体**，不是微服务架构

## 4. Monorepo 分层设计

### 4.1 根工作区

根目录的 `package.json` 负责统一编排所有工作区。当前最重要的根命令包括：

- 前端开发：`dev:user`、`dev:page`、`dev:admin`、`dev:admin:page`
- 后端开发：`dev:backend`、`dev:backend:tmux`
- 构建：`build:user`、`build:admin`、`build:backend`、`build`
- 校验：`check:user`、`check:admin`、`check:backend`、`check`
- 后端测试：`test:backend:*`
- 数据库与 RAG：`db:*:backend`
- 页面脚手架：`create:page`、`create:admin-page`

这里的设计重点不是把所有逻辑堆到根目录，而是把“多应用统一入口”放在根目录，把“真实业务实现”留在各自工作区。

### 4.2 `scripts/`

`scripts/` 是当前仓库的工程胶水层，主要承担以下职责：

- 根据 `--app user|admin` 解析目标工作区
- 读取和校验 `pages.manifest.json`
- 启动整站预览或单页预览
- 自动寻找可用端口
- 构建前执行页面结构校验
- 创建新页面目录、`Page.vue`、`mock.ts` 和 manifest 条目

当前最关键的脚本包括：

| 脚本 | 作用 |
| --- | --- |
| `scripts/dev-user.mjs` | 启动用户端或后台端开发服务，支持整站/单页模式 |
| `scripts/dev-page.mjs` | 单页预览包装器 |
| `scripts/build-user-web.mjs` | 前端构建前校验并触发对应工作区构建 |
| `scripts/validate-workspace.mjs` | 校验页面目录、`Page.vue`、`mock.ts` 与 manifest 是否一致 |
| `scripts/create-page.mjs` | 生成页面脚手架并写入页面清单 |
| `scripts/backend-smoke-*.mjs` | 后端冒烟与回归脚本 |

## 5. 前端架构

### 5.1 共同的页面运行时模型

两个前端应用虽然 UI 壳不同，但底层运行方式是一致的：

```text
index.html
  -> src/main.ts
  -> src/app/App.vue
  -> 读取 pages.manifest.json
  -> 解析运行模式
  -> 通过 page-registry 动态加载 Page.vue
```

这意味着：

- “整站运行”和“单页预览”不是两套应用
- 页面不是靠手写路由表注册，而是靠页面清单 + 目录约定发现
- 页面目录本身就是最小协作单元

页面清单位于：

- `apps/user-web/src/app/pages.manifest.json`
- `apps/admin-web/src/app/pages.manifest.json`

每个页面条目当前至少包含：

- `id`
- `title`
- `group`
- `route`
- `owner`
- `status`
- `summary`
- `folderPath`
- `modulePath`
- `mockPath`
- `legacySources`

其中 `legacySources` 的存在说明当前页面体系已经考虑了从旧小程序或旧原型迁移的追踪能力。

### 5.2 运行模式与页面发现

两个前端都通过 `resolve-config.ts` 解析运行模式：

- `app`：整站模式
- `page`：单页预览模式

来源优先级如下：

1. URL 参数：`?mode=page&page=xxx`
2. 环境变量：`VITE_IHC_MODE`、`VITE_IHC_PAGE_ID`

页面组件通过 `page-registry.ts` 使用 `import.meta.glob()` 动态发现：

- 用户端会预加载 `onboarding/intro`、`auth/login`、`auth/real-name`、`home/dashboard`
- 后台端默认按需懒加载全部 `Page.vue`

### 5.3 自定义导航而非 Vue Router

当前前端导航由 `usePageNavigation.ts` 自行维护页面栈，统一暴露：

- `navigateTo`
- `redirectTo`
- `reLaunch`
- `navigateBack`
- `canGoBack`
- `getStack`

鉴权页跳转也集成在这层导航中：

- 用户端会根据 `requiresUserAuth()` 判断未登录访问
- 后台端会根据 `requiresAdminAuth()` 判断未登录访问
- 登录前目标页会被记录，登录后再回跳

这套模型的优点是：

- 更适合当前“页面目录 + 单页预览”的协作方式
- 不需要维护复杂路由树
- 页面原型式开发和正式联调使用同一套壳

### 5.4 用户端 `apps/user-web`

用户端当前是 **移动端风格单页壳**，首页入口为 `onboarding/intro`，主要特点：

- 首页、服务、健康、社区、档案等能力都在同一应用内
- 使用 `packages/page-core` 的底部导航基础数据
- 页面壳偏移动端，适合手机宽度预览
- 页面目录普遍保留 `mock.ts`，便于脱离后端快速预览

| 分组 | 页面数 |
| --- | ---: |
| `onboarding` | 1 |
| `auth` | 4 |
| `home` | 17 |
| `service` | 23 |
| `health` | 22 |
| `healthdocs` | 7 |
| `orders` | 10 |
| `community` | 5 |
| `content` | 5 |
| `diet-record` | 2 |

当前状态上，用户端是 **“页面壳与 mock 预览优先，真实 API 逐步替换”** 的架构。代码搜索显示，当前直接引用 `src/shared/api` 的用户端页面数量为 `7`，说明用户端仍然保留了较重的页面原型属性。

### 5.5 后台端 `apps/admin-web`

后台端当前是 **桌面工作台壳**，登录入口页为 `auth/login`，主要特点：

- `App.vue` 内部直接实现了主导航、次级导航、通知面板和账号菜单
- 页面分组围绕工作台、用户管理、服务、数据分析、系统设置展开
- 页面运行模型仍与用户端保持一致，仍然基于 manifest + `Page.vue`
- 相比用户端，后台端真实 API 接入程度更高

### 5.6 前端 API 接入方式

两个前端都各自维护了 `src/shared/api/client.ts`，实现方式基本一致：

- 使用浏览器原生 `fetch`
- 约定统一响应包结构：`{ code, message, requestId, data }`
- 在本地开发环境下优先走 Vite 代理 `/api/v1`
- 若未显式配置 `VITE_API_BASE_URL`，生产默认指向 `http://server.mctown.online:8190/api/v1`

Vite 配置中已内置代理：

```text
/api/v1 -> IHC_BACKEND_TARGET 或 http://server.mctown.online:8190
```

这意味着前后端联调有两种常见方式：

- 本地前端 + 本地后端：走本地 Vite 代理
- 本地前端 + 远端后端：直接走默认远端 API 地址

## 6. 共享包 `packages/page-core`

`packages/page-core` 不是组件库，而是 **页面运行时核心的最小共享层**。当前承担的职责主要有：

- `PageEntry`、`PageComponentProps`、`NavigationApi` 等类型定义
- `normalizePageId()`、`resolveInitialPage()` 等页面解析工具
- `groupPagesByGroup()` 等页面分组工具
- 用户端底部导航基础数据 `bottomTabItems`

当前约束很明确：

- 放在这里的内容必须跨前端工作区可复用
- 不能和具体页面 UI 强绑定
- 重点服务于页面元信息、页面发现与导航运行时

## 7. 后端架构

### 7.1 后端总体形态

`apps/backend` 当前是 **NestJS 模块化单体**，而不是多个独立服务。入口在：

```text
apps/backend/src/main.ts
```

启动过程为：

1. 先执行数据库可用性引导 `bootstrapDatabase()`
2. 再创建 Nest 应用
3. 加载全局配置、CORS、全局前缀、校验、异常过滤器、响应拦截器
4. 挂载 Swagger
5. 监听 `HOST:PORT`

当前全局约定：

- API 前缀：`/api/v1`
- Swagger：`/api/v1/docs`
- CORS 来源：由 `CORS_ORIGINS` 控制
- DTO 校验：`ValidationPipe`
- 统一错误处理：`AllExceptionsFilter`
- 统一响应包：`ApiResponseInterceptor`

### 7.4 数据与基础设施

当前后端的数据与基础设施层已经明确：

| 能力 | 实现 |
| --- | --- |
| 主数据库 | `PostgreSQL` |

- AI 与检索：`AgentTask`、`AgentHumanReview`、`AgentAuditLog`、`RagKnowledgeBase`、`RagDocument`、`RagChunk`、`RagEval*`

这说明当前后端不是“接口先写，模型以后再补”的状态，而是已经具备比较完整的业务数据底座。

### 7.6 AI / Agent / RAG

后端中的 AI 能力已经作为正式模块存在，而不是临时脚本：

- 用户端 AI 接口位于 `/api/v1/app/ai/*`
- 内部多智能体治理接口位于 `/api/v1/internal/agents/*`
- Agent 任务通过 `BullMQ` 异步执行
- RAG 已具备知识库、文档、切片、构建、检索和评测模型

当前项目层面应把这部分理解为：

- **AI 是后端架构的一部分**
- 但更详细的执行模型、Agent 卡片和治理规则应以专门文档为准

## 8. 当前工程流

### 8.1 开发流

前端开发：

```bash
npm run dev:user
npm run dev:page -- --page home/dashboard
npm run dev:admin
npm run dev:admin:page -- --page dashboard/overview
```

后端开发：

```bash
npm run dev:backend
```

如果希望后端常驻在独立会话中：

```bash
npm run dev:backend:tmux
```

### 8.2 校验与构建流

整仓校验与构建：

```bash
npm run check
npm run build
```

其中：

- 前端校验以 `validate-workspace.mjs + vue-tsc` 为主
- 后端校验以 `tsc` 为主

构建输出：

- 用户端：`dist/user-web`
- 后台端：`dist/admin-web`
- 后端：`apps/backend/dist`

### 8.3 页面脚手架流

新增页面时，仓库推荐始终走脚手架：

```bash
npm run create:page -- --group health --page health-data --title "健康数据" --owner "成员A"
npm run create:admin-page -- --group elder --page member-list --title "长者档案" --owner "后台组"
```

脚手架会自动：

- 创建页面目录
- 生成 `Page.vue`
- 生成 `mock.ts`
- 可选生成 `README.md`
- 写入对应应用的 `pages.manifest.json`

这也是为什么当前仓库非常依赖“页面清单始终准确”。

### 8.4 测试流

后端当前已经有可执行测试入口：

- `npm run test:backend:unit`
- `npm run test:backend:integration`
- `npm run test:backend:smoke:baseline`
- `npm run test:backend:smoke:expanded`
- `npm run test:backend:contract:user`

与之相比，前端当前仍以页面预览、workspace 校验和类型检查为主，尚未形成成体系的自动化前端测试栈。

## 9. 当前架构边界与约束

基于现有实现，当前项目在架构表述上应坚持以下口径：

### 9.1 应该这样描述

- 这是一个 **全栈 Monorepo**
- 前端是 **双 Web 应用 + 共享页面运行时**
- 后端是 **NestJS 模块化单体**
- 页面开发的最小单元是 **页面目录**
- 页面发现的单一数据源是 **`pages.manifest.json`**
- 前端当前是 **mock 驱动开发与真实 API 联调并行**
- AI 能力已经纳入统一后端架构，而不是外挂服务

### 9.2 不应该这样描述

- 不应描述为“老人端、家属端、后台端 3 个独立前端仓库”
- 不应描述为“前端使用 Vue Router 统一路由”
- 不应描述为“后端已拆分成多服务”
- 不应忽略 `scripts/` 对页面开发和工作区校验的核心作用
- 不应把 `legacy/miniprogram-user` 误认为当前主应用

### 9.3 当前最重要的工程原则

- 页面目录、页面清单、脚手架脚本、运行时装配方式必须保持同一口径
- 新增或移动页面时，必须同步维护 manifest
- 前端联调默认围绕 `/api/v1` 展开，而不是各自发散地定义接口地址
- 后端新增能力优先补在既有模块化单体内部，而不是提前拆服务
