# IntelliHealthCare 后端设计文档

## 1. 文档目标

本文档用于说明 IntelliHealthCare 当前后端系统的设计架构、核心机制与工程边界，重点回答以下问题：

- 后端为何采用模块化单体，而不是拆分为多个独立服务；
- 用户端、后台端、系统面与内部 AI 治理面如何在同一后端内协同；
- 业务模块、数据模型、鉴权、异步任务、对象存储如何组织；
- Hermes 多智能体运行时如何嵌入后端主架构；
- RAG 知识库如何构建、授权检索、评测与服务于 Agent。

本文档描述的是当前仓库中已经实现并可从代码直接验证的后端设计，不将产品规划或概念蓝图等同于既有实现。

## 2. 后端总体定位

IntelliHealthCare 后端当前位于 `apps/backend`，采用 `NestJS + Prisma + PostgreSQL + Redis/BullMQ + MinIO` 的模块化单体架构。其职责不是单纯提供 CRUD 接口，而是统一承接四类能力：

- 用户端业务 API：`/api/v1/app/*`
- 后台业务 API：`/api/v1/admin/*`
- 系统自检与架构信息 API：`/api/v1/system/*`
- 内部多智能体与 RAG 治理 API：`/api/v1/internal/agents/*`

这一定位意味着后端既是交易与档案系统，也是 AI 增强能力的受控运行底座。AI 不被设计为独立平台，而是被纳入业务权限、数据边界、审计和人工复核体系之内。

## 3. 设计原则

当前后端设计体现出四个稳定原则：

- 以领域边界组织系统，而不是按前端页面拆散后端能力；
- 以统一权限、统一数据和统一审计承接 AI，而不是绕开业务层直接落库；
- 以模块化单体保证联调效率和跨域协作，再为后续拆分保留边界；
- 以“关系模型 + JSON 扩展字段”同时承接稳定交易数据与持续演进的 AI/RAG 元数据。

## 4. 总体架构

```text
User Web / Admin Web / Internal Calls
                |
                v
        NestJS Controllers
                |
                v
        Domain Application Services
                |
      +---------+---------+-------------------+
      |                   |                   |
      v                   v                   v
 Prisma/PostgreSQL   Redis + BullMQ      MinIO
      |                   |
      +---------+---------+
                |
                v
     Hermes Agents Runtime + RAG Layer
                |
      +---------+---------+-------------------+
      |                   |                   |
      v                   v                   v
 Agent Registry      LLM Gateway      Embedding Gateway
      |                   |                   |
      +---------+---------+-------------------+
                |
                v
        Tool Layer + Knowledge Retrieval
```

从实现上看，后端可划分为五层：

- 接口层：控制器、DTO、Swagger、路径前缀与鉴权入口；
- 领域层：`users`、`orders`、`reports`、`community`、`agents` 等模块服务；
- 基础设施层：`PrismaService`、`QueueService`、`StorageService`；
- AI 增强层：Hermes 编排、LLM/Embedding 网关、受控工具层、RAG 检索；
- 工程治理层：环境变量校验、开发数据库回退、迁移、种子、测试与联调文档。

当前对外交互仍以 `REST API` 为主。代码中尚未启用实际的 `WebSocket Gateway`，异步协同主要通过 `BullMQ Worker` 在后端内部完成。

## 5. API 面与运行边界

后端当前对外呈现四个正式接口面：

| 接口面 | 路径前缀 | 使用对象 | 设计意图 |
| --- | --- | --- | --- |
| `app` | `/api/v1/app` | 长者与家属 | 承接用户端业务流程与 AI 助手能力 |
| `admin` | `/api/v1/admin` | 运营、医生、护理、机构人员 | 承接后台工作台与管理能力 |
| `system` | `/api/v1/system` | 运维、联调、说明性调用 | 提供健康检查与架构摘要 |
| `internal` | `/api/v1/internal/agents` | 内部 AI 治理链路 | 提供 Agent 任务、复核、审计、RAG 管理 |

这四个接口面并不对应四套独立系统，而是同一领域模型在不同安全边界上的投影。一个领域模块可以同时暴露 `app` 和 `admin` 控制器，但共享同一套核心业务服务和数据库模型。例如：

- `orders` 同时对用户端提供下单、改约、售后能力，对后台提供订单与工单管理能力；
- `reports` 同时对用户端提供报告查询，对后台提供审核与运营视图；
- `files` 同时服务用户端与后台端，但在对象键前缀和访问控制上做区隔。

因此，本系统的主组织单元是领域模块，而不是接口前缀本身。

## 6. 应用分层与模块设计

### 6.1 `common` 横切层

`common` 用于集中放置全局约束与横切能力，主要包括：

- `config`：基于 `zod` 的环境变量归一化与校验；
- `auth`：`JwtAuthGuard`、`RolesGuard`、`InternalAccessGuard`、`CurrentUser`；
- `http`：统一成功响应包装、异常过滤、Swagger 增强；
- `middleware`：请求级 `requestId` 注入；
- `utils`：时间、分页、JSON、安全序列化等通用工具。

这一层保证不同模块不重复实现基础治理逻辑，并统一系统的外部行为。

### 6.2 `infra` 基础设施层

后端基础设施被收敛为三个服务：

- `PrismaService`：统一管理 PostgreSQL 连接与 ORM 访问；
- `QueueService`：统一管理 Redis 连接与 BullMQ 连接复制；
- `StorageService`：统一管理 MinIO 客户端、Bucket 初始化、预签名上传和对象 URL。

这三个服务不直接承载业务语义，但为所有业务模块和 AI 模块提供底层能力。

### 6.3 业务与能力模块

当前 `AppModule` 实际挂载了 `17` 个应用模块：

| 模块 | 主要职责 |
| --- | --- |
| `system` | 服务健康检查、架构摘要 |
| `auth` | 用户端与后台端登录、刷新令牌、退出、公开协议 |
| `users` | 当前用户、个人资料、首页聚合、城市、搜索、积分、足迹、设置 |
| `family` | 家属绑定与地址管理 |
| `health-archive` | 基础档案、病史、风险标签、长期记忆 |
| `health-metrics` | 设备、指标、趋势、用药 |
| `health-lifestyle` | 饮食记录与自测相关能力 |
| `service-catalog` | 服务分类、列表、详情 |
| `orders` | 预约、订单、工单、评价、售后、后台派单 |
| `payments` | 支付单与支付状态确认 |
| `reports` | 报告列表、详情、解读入口、后台审核 |
| `files` | 用户端与后台端文件上传元数据 |
| `messaging` | 通知、会话、后台消息活动 |
| `community` | 话题、帖子、评论、活动报名与互动 |
| `content` | 健康资讯、讲堂、疾病知识 |
| `agents` | 用户端 AI 能力、内部多智能体与 RAG 管理 |
| `admin` | 后台概览、长者详情、分析与配置聚合 |

其中一部分模块以单一接口面为主，例如 `community`、`content`、`health-archive`；另一部分模块跨越 `app` 与 `admin` 双接口面，例如 `orders`、`reports`、`files`、`messaging`。这种设计避免了按前台/后台复制领域逻辑。

## 7. 数据模型设计

### 7.1 数据库总体策略

当前数据层以 `PostgreSQL + Prisma` 为核心，`schema.prisma` 已定义 `66` 个模型。模型设计总体上分为两类：

- 强结构化关系数据：用户、角色、家庭关系、设备、服务、订单、支付、报告、消息等；
- 半结构化扩展数据：健康档案摘要、报告摘要、订单 AI 摘要、RAG 元数据、Agent 输出、审计快照等。

因此，后端并未把 AI 引入理解为“额外外挂数据”，而是把 AI 过程数据与业务主数据一并纳入同一关系数据库，以便统一权限、追踪和审计。

### 7.2 核心聚合划分

从当前 schema 看，数据模型主要围绕以下聚合展开：

- 身份与组织：`User`、`Role`、`UserRole`、`Institution`、`Staff`
- 家庭与地址：`FamilyBinding`、`Address`
- 健康档案：`HealthArchive`、`HealthMetricRecord`、`HealthAlert`、`Medication`、`DietRecord`、`SelfTestAttempt`
- 服务履约：`ServiceItem`、`Order`、`OrderTimeline`、`WorkOrder`、`AfterSaleRequest`、`OrderReview`
- 资金与支付：`PaymentOrder`、`RefundOrder`
- 报告与文件：`Report`、`FileAsset`
- 消息与会话：`Conversation`、`ConversationParticipant`、`ConversationMessage`、`Notification`
- 内容与社区：`Article`、`Lecture`、`DiseaseKnowledge`、`CommunityPost`、`Activity`
- AI 治理：`AgentTask`、`AgentHumanReview`、`AgentAuditLog`
- RAG：`RagKnowledgeBase`、`RagDocument`、`RagChunk`、`RagIngestionRun`、`RagEvalRun`、`RagEvalCaseResult`

### 7.3 关系模型与 JSON 并存的原因

当前 schema 中大量使用 `Json` 字段，这不是设计松散，而是为了容纳以下不断演进但又需要入库治理的数据：

- 健康档案中的基础资料、病史、长期记忆；
- 报告摘要、订单 AI 摘要、服务知识片段；
- Agent 输出、trace、审计快照与复核结论；
- RAG 的访问策略、来源配置、分块配置、评测结果。

这使系统在保持主事务模型稳定的同时，能够吸收 AI 场景中的结构迭代。

## 8. 请求处理与安全设计

### 8.1 启动与请求处理链路

应用入口位于 `src/main.ts`。当前请求链路可概括为：

```text
HTTP Request
 -> RequestContextMiddleware 生成 requestId
 -> Guard 鉴权 / 角色 / 内部来源校验
 -> ValidationPipe 做 DTO 校验与类型转换
 -> Controller
 -> Service
 -> ApiResponseInterceptor 统一包装成功响应
 -> AllExceptionsFilter 统一包装错误响应
```

这保证了后端对所有模块输出一致的响应结构：

- 成功：`{ code: 0, message: "ok", requestId, data }`
- 失败：按 HTTP 状态映射到统一业务码，如 `40001`、`40003`、`40400`、`50000`

### 8.2 鉴权模型

系统当前使用 `JWT` 区分两类登录作用域：

- `app`：面向用户端；
- `admin`：面向后台端。

JWT 载荷中除了用户身份，还携带：

- `type`
- `roles`
- `scope`
- `realName`

这意味着同一个用户体系之上，可根据不同作用域投射出不同的接口访问能力。

### 8.3 后台角色与内部接口二次校验

后台接口在 `JWT` 基础上再叠加 `RolesGuard`。而 `internal/agents` 接口进一步叠加：

- `admin` scope 校验；
- 角色校验；
- 来源 IP 白名单校验；
- 可选的 `X-Internal-Token` 共享密钥校验。

因此，内部 AI 治理面并不等同于普通后台接口，而是一个额外收紧的受控面。

## 9. 基础设施运行机制

### 9.1 开发数据库回退

`bootstrapDatabase()` 是当前后端的重要工程特性。若开发环境的 PostgreSQL 不可达，且启用了回退配置，系统会：

- 自动启动嵌入式 `PGlite`；
- 通过 `PGLiteSocketServer` 暴露 PostgreSQL 兼容连接；
- 自动执行 Prisma migration；
- 根据配置自动执行 seed。

这一机制只在开发环境使用，其目标是保证本地自举速度和团队联调一致性，而不是替代正式数据库。

### 9.2 Redis 与 BullMQ

Redis 当前主要承担：

- BullMQ 队列连接；
- Agent Worker 执行基础；
- 系统健康检查。

在当前设计中，Redis 不是通用缓存中心，而是后端异步任务的基础设施。真正进入队列的关键场景是 `AgentTask`。

### 9.3 对象存储

`StorageService` 统一封装 MinIO/S3-compatible 存储能力，负责：

- Bucket 自动创建；
- 预签名上传 URL 生成；
- 已上传对象存在性校验；
- 对象公网 URL 生成。

文件上传流程采用两阶段设计：

```text
业务接口申请 presign
 -> 客户端直接 PUT 上传到 MinIO
 -> 业务接口 complete，校验对象大小与键前缀
 -> 写入 FileAsset 元数据
```

该流程避免大文件穿过业务服务进程，同时保持元数据和权限归属仍由后端掌控。

## 10. 业务流程设计特征

### 10.1 领域服务作为核心协调者

从现有模块实现看，控制器普遍较薄，主要负责：

- 解析参数；
- 触发鉴权；
- 调用服务；
- 返回标准化结果。

真正的业务协调发生在服务层。例如：

- `OrdersService` 同时处理可访问长者解析、地址校验、价格预览、订单状态流转与时间线记录；
- `UsersService` 在同一接口中聚合用户主资料、足迹、评价、优惠券和家庭绑定关系；
- `AppMessagingService` 统一承接通知、会话与后台消息活动。

这说明当前设计强调“领域服务聚合”，而不是把业务逻辑分散到控制器或基础设施层。

### 10.2 用户端与后台端共享主数据

当前系统并未为后台单独建设一套数据副本。后台页面看到的订单、报告、消息、长者详情，均与用户端共享主表和主交易状态。后台更多是面向同一主数据的治理与分析投影。

这一设计减少了数据同步复杂度，也为 AI 在不同端统一消费同一上下文提供了条件。

## 11. Hermes 多智能体运行时设计

### 11.1 系统定位

Hermes 在本项目中的定位是后端内部的受控多智能体运行时，而不是开放自治平台。其作用是：

- 承接用户端 AI 能力与后台 Copilot 能力；
- 为领域 Agent 提供统一编排、工具调用、模型调用和审计机制；
- 将高风险 AI 输出纳入人工复核链路。

换言之，Hermes 是后端主架构的一部分，不是另起炉灶的第二后端。

### 11.2 运行时组件

`agents` 模块当前由以下核心部件组成：

- `AgentRegistry`：注册 Agent 定义、输入输出 schema、允许工具与禁用动作；
- `AgentTaskService`：创建任务、状态持久化、重试控制；
- `AgentDispatchService`：把任务投递到 BullMQ；
- `AgentTaskProcessor`：Worker 侧执行入口；
- `AgentOrchestratorService`：核心编排器，负责路由、协作、工具调用与结果封装；
- `AppAgentService`：面向用户端 AI 能力的同步服务门面；
- `AgentGovernanceService`：人工复核与审计治理；
- `LlmGateway` 与 `EmbeddingGateway`：统一模型调用与降级；
- 工具层：`ReportsTool`、`HealthArchiveTool`、`HealthMetricsTool`、`ServiceCatalogTool`、`RagRetrievalTool`。

其核心运行链路如下：

```text
创建 AgentTask
 -> 持久化到 PostgreSQL
 -> 同步执行或投递 BullMQ
 -> AgentOrchestrator 解析执行计划
 -> 调用受控工具 / LLM / RAG
 -> 写回 result.trace
 -> 需要时生成 AgentHumanReview 与 AgentAuditLog
```

### 11.3 Agent 角色划分

当前统一蓝图在代码中已收敛为 `9` 个核心 Agent：

- 控制层：`TaskOrchestratorAgent`
- 交互层：`AssistantConversationAgent`、`OperationsCopilotAgent`
- 领域层：`HealthManagementAgent`、`CareCoordinationAgent`、`RiskOperationsAgent`、`DeviceOperationsAgent`、`ContentActivityOpsAgent`
- 治理层：`SafetyReviewAgent`

同时保留了 `intent-router`、`report-summary-agent`、`service-recommendation-agent` 等旧别名兼容层。

### 11.4 同步与异步双运行模式

Hermes 当前不是单一执行模式，而是区分两类入口：

#### 1. 用户端 AI 同步入口

`AppAgentService` 面向 `app/ai` 接口时，采用“同步执行但全量持久化”的策略：

- 先创建 `AgentTask`；
- 直接在请求线程中执行 `AgentOrchestrator`；
- 仍然把运行状态、输出与 trace 写回数据库；
- 立即返回给用户端，以满足交互时延要求。

这适用于：

- 助手会话；
- 服务推荐；
- 预约预填；
- 健康摘要；
- 报告解读；
- 知识检索。

#### 2. 内部治理异步入口

`internal/agents/tasks` 走标准异步队列模式：

- 创建 `AgentTask`；
- 投递 `BullMQ`；
- 由 `AgentTaskProcessor` 异步消费；
- 根据错误类型决定是否重试；
- 最终落库为 `SUCCEEDED` 或 `FAILED`。

这适用于后台运营、风险任务和需要批量调度的内部场景。

### 11.5 工具边界与治理约束

当前 Agent 并不允许无边界直接写库。其边界约束体现在两个层面：

- Agent 定义层显式声明 `allowedTools`、`forbiddenActions`、`humanReviewRequired`；
- 工具层全部通过受控服务读取业务上下文，而不是让模型直接访问数据库。

例如：

- 健康管理 Agent 可以读取报告、档案、指标与知识库，但被禁止做医疗最终决策；
- 服务协同 Agent 可以检索服务目录、地址和排班信息，但不能自动下单或自动派单；
- 风险运营 Agent 可以做识别与分诊建议，但不能直接触发最终状态变更。

### 11.6 审计与人工复核

Hermes 的治理闭环已在数据模型上落地为：

- `AgentTask`：任务主记录与执行结果；
- `AgentHumanReview`：人工复核工单；
- `AgentAuditLog`：全链路事件审计。

当任务命中高风险规则或安全门禁时，系统会：

- 生成人工复核记录；
- 将 payload、output、trace 快照入库；
- 追加审计日志；
- 将治理结果附着回任务结果。

这使 AI 输出从一开始就被设计为可回放、可复核、可审计。

## 12. 用户端 AI 接入设计

用户端 AI 并未被实现为独立的聊天系统，而是复用现有业务模型：

- 会话使用 `Conversation`；
- 参与者使用 `ConversationParticipant`；
- 消息使用 `ConversationMessage`；
- AI 推理过程使用 `AgentTask`；
- 高风险结果使用 `AgentHumanReview` 与 `AgentAuditLog`。

因此，AI 对话、健康总结、报告解读等能力并不是“外部插件式调用”，而是被纳入业务主数据体系，能够自然连接用户身份、家庭授权、报告上下文和服务流程。

## 13. RAG 知识系统设计

### 13.1 设计目标

本项目的 RAG 不是孤立检索服务，而是为 Hermes 与用户端 AI 提供受权限约束的可引用知识上下文。其目标包括：

- 将公共知识、机构知识和用户私有知识纳入统一检索框架；
- 为 Agent 输出提供 citation，而非无来源回答；
- 把知识构建、权限校验与评测结果纳入数据库治理。

### 13.2 知识分层模型

当前 `RAG` 使用三层可见性和五类知识类型组织知识库：

#### 可见性

- `PUBLIC`
- `INSTITUTION`
- `USER_PRIVATE`

#### 知识类型

- `SERVICE_CATALOG`
- `HEALTH_KNOWLEDGE`
- `PLATFORM_RULE`
- `INSTITUTION_RESOURCE`
- `USER_PRIVATE_ARCHIVE`

### 13.3 知识库构建结果

`build-rag-db.ts` 当前会实际构建以下知识层：

- 公共服务目录知识库：由 `ServiceItem`、机构服务信息生成；
- 公共健康知识库：由 `WHO`、`CDC`、`MedlinePlus` 公开页面，以及站内 `Article`、`Lecture`、`DiseaseKnowledge` 生成；
- 平台规则知识库：由 Hermes 相关仓库文档与系统规则条目生成；
- 机构资源知识库：按机构维度从 `Institution`、`Staff`、`StaffSchedule`、`ServiceItem` 生成；
- 用户私有档案知识库：按用户维度从 `HealthArchive`、`Report`、`HealthMetricRecord`、`Order` 和 `FamilyBinding` 生成。

这说明项目中的 RAG 并不是“一个大索引”，而是按权限边界拆分的知识集合。

### 13.4 文档、分块与索引设计

RAG 数据模型由以下实体组成：

- `RagKnowledgeBase`
- `RagDocument`
- `RagChunk`
- `RagIngestionRun`
- `RagEvalRun`
- `RagEvalCaseResult`

当前分块策略在构建脚本中默认为：

- `paragraph-window`
- 目标长度 `820` 字符
- 重叠 `140` 字符
- 最小块长 `180` 字符

每个 chunk 额外保存：

- `headings`
- `keywords`
- `embedding`
- `embeddingModel`
- `visibility`
- `ownerUserId` / `institutionId`

这使检索结果天然具备引用与权限信息。

### 13.5 检索授权模型

RAG 当前按调用方区分三种检索入口：

#### 1. App 检索

`GET /app/ai/knowledge/search` 默认只检索 `PUBLIC`。当显式传入 `includePrivate=true` 时，才会在本人或已授权家属范围内联查 `USER_PRIVATE`。用户端不开放 `INSTITUTION_RESOURCE`。

#### 2. Internal 检索

`POST /internal/agents/rag/search` 面向后台与内部治理面，支持按知识类型、可见性、`ownerUserId`、`institutionId` 精确过滤，并受后台 Token、来源 IP 和可选共享密钥约束。

#### 3. Agent 工具检索

Hermes 通过 `searchKnowledgeBase` 工具调用 RAG。Agent 检索在公共知识之外，可按当前 actor 身份补充私有知识或机构知识，但仍受业务授权约束。

### 13.6 检索算法与降级策略

当前检索流程为：

```text
规范化 query
 -> 中文/英文 token 切分
 -> 词法候选召回
 -> 生成 query embedding
 -> 词法分 + 余弦相似度重排
 -> 返回 excerpt + matchedTerms + citation
```

其中：

- 候选召回依赖标题、正文、关键词、标题层级等词法命中；
- 排序采用词法分与向量相似度混合；
- 若 embedding 未配置，则自动退化为确定性向量或纯词法检索，不阻塞主流程。

### 13.7 RAG 评测闭环

`eval-rag.ts` 已实现检索评测闭环，并将结果落库到：

- `RagEvalRun`
- `RagEvalCaseResult`

当前记录的核心指标包括：

- `passRate`
- `hit@1`
- `hit@3`
- `hit@5`
- `MRR`

这意味着 RAG 在本项目中不是“手工看起来能搜到就算完成”，而是进入了结构化评测阶段。

## 14. 模型网关与降级设计

### 14.1 LLM 网关

`LlmGateway` 当前统一封装：

- 结构化对象生成；
- tool-calling 生成；
- 主模型、轻量模型与 fallback 模型切换；
- DeepSeek、OpenRouter、OpenAI-compatible 兼容；
- 失败时的确定性输出降级。

因此，业务模块和 Agent 编排层不直接依赖某个具体模型提供商。

### 14.2 Embedding 网关

`EmbeddingGateway` 统一封装：

- embedding 提供商解析；
- 模型与超时配置；
- fallback 向量生成；
- 与 LLM 配置的默认继承关系。

这样做的结果是：即便真实向量模型暂未配置，RAG 与 Agent 运行时仍可继续工作，只是退化为保守模式。

## 15. 工程化与质量保证

### 15.1 配置与迁移

后端通过 `env.schema.ts` 对运行时环境进行强校验，并已存在多批 Prisma migration。数据库结构变更不是隐式的，而是通过迁移文件受控演进。

### 15.2 Swagger 与联调

`main.ts` 对 Swagger 做了明显增强：

- 自定义标签顺序；
- 联调说明面板；
- Token 使用提示；
- Issue 反馈入口；
- API 复制按钮。

这说明当前后端不仅提供 OpenAPI 描述，而且把前后端联调作为设计对象之一。

### 15.3 测试分层

当前后端已经具备三层验证能力：

- 单元测试：覆盖环境配置、密码、内容、文件、用户服务、Agent 治理与编排等；
- 集成测试：覆盖认证、后台主流程、文件上传等；
- 冒烟回归：通过根级脚本执行后端回归检查。

因此，当前后端并非“仅靠 Swagger 人工点击验证”的状态。

## 16. 当前后端设计结论

IntelliHealthCare 当前后端可以概括为：

> 一套以模块化单体为骨架、以 PostgreSQL 为主数据中心、以 Redis/BullMQ 承接异步协同、以 MinIO 承接文件对象、并将 Hermes 多智能体与 RAG 知识系统内嵌进业务权限和审计体系中的统一后端架构。

这套设计的关键价值不在于堆叠大量中间件，而在于：

- 以统一领域模型承接用户端、后台端和 AI 增强能力；
- 以共享权限、共享主数据和共享审计控制 AI 的运行边界；
- 以知识分层和评测闭环避免把 RAG 退化为无治理的文本检索；
- 以工程化回退、迁移、测试和文档机制维持后端可开发、可联调、可扩展。

从当前代码形态看，这是一套强调业务闭环、AI 受控落地与工程可维护性的后端设计，而不是将业务服务与 AI 运行时割裂处理的拼接式方案。
